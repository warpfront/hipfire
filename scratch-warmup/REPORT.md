# gfx1201 57k first-request warmup: cold kernel JIT, not VMM or scratch

## Result

**No runtime fix.** The reported 37.5 s first request versus 22.0 s warm request is reproducible when the on-disk kernel cache is empty. On the same card-C, model, binary, process and two **uncached** 57k prompts, first-ever TTFT was **37.620 s**, and the second was **22.083 s** (15.537 s gap). Instrumentation measured **18.462 s of CPU-side HIP kernel compilation** in the first request and none in the second. This sum is not additive to the wall-time gap: GPU work already enqueued can execute while the CPU compiles later kernels. A *new daemon process using the cache populated by that first request* took **21.792 s** on its first request, with just 1.6 ms of cache lookup and no JIT. The normal persistent, content-addressed `HIPFIRE_KERNEL_CACHE` already provides the cheapest fix: retain/populate it. Eager recompilation, premature VMM allocation, or scratch pre-sizing would move the cost into model load or increase VRAM, not improve an already-cached first request.

The previous landed 0.4.0 card-B measurement (`wt-land040/scratch-land040/card-b/warm-{first,uncached}.timing.json`) was 37.508/22.014 s. Its prior same-text retry cached 49,152 prompt tokens and was **not** used as the warm baseline. This report uses the separate card-C `GPU-085289909a86cc63` under `ROCR_VISIBLE_DEVICES=HIP_VISIBLE_DEVICES=GPU-085289909a86cc63` and the exact original `wt-deepctx/scratch-deepctx/prompt.request.json` fixture (prompt MD5 `0c939a51f79435d6aa9fd01987dda078`; server 57,030 tokens). For the warm request, only the opening was changed to `Different opening: `, yielding 57,034 tokens and **0 cached tokens**, versus 57,030 and **0 cached tokens** first. Both HTTP responses were 200, produced one token (`The`), and had identical model, temperature and thinking settings. No 5,909-token proxy was used.

## Attributed phases

Temporary, opt-in `HIPFIRE_WARMUP_PROBE` instrumentation timed the existing `KernelCompiler::compile`, HIP module loading, every `grow_vmm_tensor` map, `KvCache::ensure_mapped_capacity`, owned PBS acquisition, and prefill chunk dispatch. These are synchronous **host interval sums**, not GPU timings. Instrumentation was fully removed before commit. The process was pre-warmed and listening **before** request timing; model load and the initial 32 VMM mappings of 64 MiB are excluded from the request-phase rows. `HIPFIRE_GRAPH=1`; the request enters eager multi-token prefill, not the single-token AR graph path. The same-source uninstrumented baseline was run separately.

| Phase (request only) | First request, empty kernel cache | Second request, same process, zero prompt-cache tokens | First request, *new process*, now-populated kernel cache |
|---|---:|---:|---:|
| HTTP request-to-completion/first token | **37.620 s** | **22.083 s** | **21.792 s** |
| Kernel compile/cache lookup (`compile`) | **18.462 s**; 42 calls, 38 new `.hsaco` objects | 0 calls | **0.0016 s**; 42 cache hits |
| HIP module/code-object load | **0.0288 s** | 0 | **0.0083 s** |
| VMM growth (`hipMemCreate/Map/SetAccess` within 224 `map_next` calls) | **0.0409 s**, 1.750 GiB | **0**, no growth | **0.0057 s**, 224 calls, 1.750 GiB |
| Complete `ensure_mapped_capacity` (includes preceding map time; do not add) | **0.0418 s** | ~0 | **0.0064 s** |
| PBS scratch acquisition (first chunk only; then reused) | **0.0696 s** | ~0 | **0.0051 s** |
| GPU prefill, dispatch/host/tokenization | Remaining overlapping work; warm request establishes **22.083 s** comparable end-to-end floor | Same model work | **21.792 s** |

The seven admitted chunks were 8192×6 plus a 7878-row final chunk; log receipt `requested=8192 admitted=8192 commit_stride=512`. One initial PBS allocation, then zero-duration reuse; no increasing PBS rung allocations. Graph capture cannot explain the cold delta: the route is eager 8192-row prefill and only a single output token was requested; no separate capture interval appears. Code-object loading is tens of milliseconds, VMM ~41 ms even on empty cache, scratch ~70 ms; none can account for 15.5 s. The VMM path maps 32 K/V owners at each of seven 8192-token horizons (224 growth calls), but batching those maps could save only the measured map interval, not seconds. `KV cache: Fp8 vmm (16/64 layers carry KV; K/V 1032B/row...)` and `max_seq=262144` appear in **each** daemon log: no Q8 substitution.

With a partial pre-existing shared cache, uninstrumented first/warm requests were 31.926/21.979 s, and the daemon logged eight stale/missing code objects recompiling. Cloning that now-warm cache then evicting precisely those eight `.hsaco` files in a separate throwaway cache produced first/warm 25.071/22.133 s; timed compilation was 3.496 s on that invocation. The exact absolute cold penalty varies with OS/toolchain page cache, but cache misses explain its direction and size. A fully warm cloned-cache daemon independently gave 21.818/22.109 s first/warm. The pristine-cache run's 38 newly generated code objects survived process teardown; the subsequent daemon made 42 successful in-process `compile()` calls in 1.6 ms total and **zero** new compilations. This is a durable on-disk cache hit, not only a same-process module reuse.

## Provenance and decision

Source and executable base: `e5f944a3aacc67652b773b8f14d81cb4dcde367a` (0.4.0), built locally with `cargo build --release`; the instrumented daemon was built with `cargo build --release -p hipfire-daemon --bin daemon`, MD5 `5768c8d2f9a78394e6161af8a124fafa`. CLI MD5 `79041e021373bf438432049518a8b491`; model MD5 `2cfe88923b3671ca16a8de6ec1122fde`. Actual server used knob-free native fp8 VMM (`requested mode=auto, effective KV=fp8`) with explicit `HIPFIRE_GRAPH=1`, kernel cache path set per arm, and otherwise a fresh isolated HOME; no source feature flags or KV overrides. Response/timing JSON and daemon logs live beside this report (`profile-pristine*`, `profile-warmcache*`, `profile-8miss*`, `baseline-*`, `fresh2-response.json`), with 57,030/57,034 token counts and cache-hit details in the response artifacts. `profile-pristine.log` includes the load and both HTTP request windows; `profile-pristine-fresh2.log` is the subsequent fresh process on the very same cache directory. Measurements were made on card-C, never card-B; the card-B regression guard is conditional on implementing a fix and was therefore not run. Production source edits and temporary instrumentation were removed, so there is no behavior change requiring a guard or quality rerun.
