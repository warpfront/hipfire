### Changes: G12 engine loop, Gemma 4 EAGLE window lanes

- **Concurrent Gemma 4 EAGLE requests decode together (HIPF-642; `generation.engine_loop = engine` with `serve.vmm_batch` and a drafter).** The Gemma 4 lanes now run speculative windows when the load has the EAGLE drafter and `serve_vmm_batch.spec` is on. Each lane holds a fork of the drafter: the weights and the per-round scratch are shared, and each fork has its own conditioning hidden. A greedy EAGLE request moves into a lane at a window boundary, with its KV rows and its drafter state. Each window epoch runs every lane's window, the same `mtp_step` as the singleton, on the lane's caches. Before, every EAGLE request stayed on the resident state until it finished, so k>1 requests ran one after the other. Sampled and penalized EAGLE requests stay on the resident state. The load ack reports `continuous_batch_spec_mode: "eagle"`.
- **`continuous_batch.max_active_lanes` on the engine loop counts the requests that hold state at the same time.** Before, the engine loop always reported 1.
- **`scripts/engine_loop_ab.py` `conc.require_overlap` gates only `batch` arms.** A `noslots` arm runs one request at a time by design, so the EAGLE route could not pass with its `engine-noslots` arm.
