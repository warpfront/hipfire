### Fixes: G12 engine loop, Gemma 4 prefix reuse

- **Gemma 4 reuses the earlier turns of a conversation (HIPF-598).** The Gemma 4 chat template drops the thinking-off primer (`<|channel>thought\n<channel|>`) of earlier model turns, so a follow-up prompt never holds the previous reply at the positions it was decoded at. Gemma 4 kept snapshots only at the prompt rounded down to the prefill width and every 1024 tokens, so a follow-up turn of a prompt shorter than 256 tokens reused 0 tokens on both loops. In the first 256 prompt tokens the snapshot boundaries are now the position after each end-of-turn token (`<turn|>`); above them they stay on the 256-token chunk grid (256, every 1024 tokens, the prompt rounded down to 256). The prefill splits its chunks at each boundary, and each boundary depends only on the tokens before it, so a cached turn stays byte-identical to a cold prefill: the next turn of a short conversation resumes after the last end-of-turn token of its previous prompt, a longer conversation at its previous prompt rounded down to 256. The new chunk split changes the prefill bits of a chat prompt once (an intended diff): the tokens of a prompt with a turn end in its first 256 tokens can differ from builds before this change.
- **A client cancel of an AR request on the engine loop keeps the snapshots its prompt captured (HIPF-598).** The singleton route and a resident request on the N-request scheduler now publish the turn's prompt snapshots before the rollback, as a speculative cancel does.
- **The lane marks of the engine live in the runtime session driver (HIPF-598).** `SessionDriver::mark_lane`, `lane_mark`, `lane_rewinds`, `continue_lane` and `drop_lane_mark` replace the Qwen4 bundle's own mark list: a family declares only how its state moves between the resident slot and a lane. Qwen4 behaviour is unchanged.
