- Model: `qwen3.8-27b.mq4l` (fixture pin md5 `d020f248…`, carried over).

## What changed

One 256-thread workgroup per (kv head, tile) serves all six q heads:
K tile read once from global (key-partitioned 8 waves x 16, no K LDS),
V in 32-key LDS slabs, Q FWHT-rotated once at stage-in; same partials
ABI (existing reduce consumes unchanged). Dispatch fires only for
gfx1100 + H24/KV4/D256 + `v_mode==8` (Q8_0 V); lloyd V keeps the scalar
tile (GQA loses there at every ctx). LDS ~17.5 KB -> 3 WGs/CU.

## Correctness (all on the claim tree or logically identical gated builds)

- `tmp_fwht_gqa_oracle` (lab-gated, kept in-tree): bit-identical vs the
  scalar tile on T=1/2/16/17/32/128/256/66048 x q8/lloyd4 synthetic
  inputs (the 516-tile case reproduces the production 512-wide grid with
  multi-iteration blocks); both V accumulations use the scalar-identical

  lloyd4 battery likewise 10/10 (scalar path, unaffected).
- KLD WT2 mq4l fwht4/q8 24-chunk: 0.033336, `.kldseq` bit-identical to
  the pre-P4a baseline (`530906ff…`); GQA touches nothing in prefill.

## Explicitly parked (same branch, separate commit)

- lloyd4 V GQA (v1 full-tile LDS + v2 key-partitioned): correct
  (oracle + 10/10) but slower at every ctx (-2% short, -9% medium,
  -44% long v1). The loss scales with ctx, so per-tile overhead was the
  wrong model; needs device-side profiling before any v3. Dispatch arm
  covers v_mode 8 only; lloyd paths untouched.
- P4 batched-tile work, fwht3/v2/v3 fast paths: untouched (no fixtures,
  no batch-lane validation on this box).
