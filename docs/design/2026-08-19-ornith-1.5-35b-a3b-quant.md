# Ornith 1.5 35B-A3B — hipfire quantization (qt44 MQ4 v2) — design

**Status of every claim below: `planned`.** Nothing here is `measured` or
`branch-implemented`. Tensor-layout and config facts are read from the published
HuggingFace `config.json` and `model.safetensors.index.json` and are marked as
such; everything downstream of them is intent.

**Branch:** `quant/ornith-1.5`, stacked on `quant/quality` (PR #599), which is
itself stacked on `feat/ternary-bonsai-27b` (PR #597). Stack depth 3.
Base commit `3243261ea`. Pushed to `warpfront`, never the fork.

**Goal:** ship `ornith-ai/Ornith-1.5-35B-A3B` as a pullable hipfire SKU in
**qt44 MQ4G256V2**, the format PR #599 introduces, with a text decoder, an MTP
sidecar, and the vision tower.

## Why this stacks on #599

On `quant/quality`, `--format mq4` routes to qt44 MQ4 v2
(`crates/hipfire-quantize/src/pipeline.rs:240`), not the historical qt13. #599
also lands the `saddle-quant` crate, which is the only KLD apparatus in the tree
whose output can support a published quality claim. Both are prerequisites for
this work, so this branch stacks rather than targeting master.

This branch must not modify #599's qt44/qt45 internals. The ownership audit is
the same form #599 used against #597:

```
git diff -G'MQ4G256V2|MQ4CG256|qt.?44|qt.?45' 3243261ea -- crates
```

Expected empty at review time.

## The model (read from published config + index.json)

`ornith-ai/Ornith-1.5-35B-A3B`, 71.9 GB BF16 across 33 files, 1811 tensors.
`Qwen3_5MoeForConditionalGeneration` / `model_type: qwen3_5_moe` ⇒ **arch_id 6**
via `MODEL_TYPE_TO_ARCH_ID` (`crates/hipfire-runtime/src/arch_mapping.rs:43`).

- 40 layers, DeltaNet hybrid `linear_attention ×3 → full_attention`
  (`full_attention_interval: 4`).
- hidden 2048, 16 attn heads / 2 KV / **head_dim 256**, **partial_rotary 0.25**,
  `attn_output_gate: true`, θ=1e7, mrope `[11,11,10]` with
  `mrope_interleaved: true`.
- MoE: 256 experts / top-8, `moe_intermediate_size 512`.
- **`shared_expert` + `shared_expert_gate` per layer**,
  `shared_expert_intermediate_size: 512`.
- vocab 248320, `tie_word_embeddings: false`.
- Vision tower: depth 27, hidden 1152, patch 16, spatial_merge 2,
  out_hidden 2048, `deepstack_visual_indexes: []` (no deepstack).

### Two deltas from ORNITH 1.0, both consequential

1. **Main-body experts are canonical stacked-3D**
   (`model.language_model.layers.N.mlp.experts.gate_up_proj`). ORNITH 1.0 AEON
   shipped these *un-stacked* and required the arch-6 fusion branch added in
   `54e99d9d` (see `docs/design/2026-07-03-qwen35-dspark-port.md`). Ornith 1.5
   does not hit that path. This is the single largest reason the text quant is
   expected to need little or no quantizer change.

2. **The MTP module's 256 routed experts *are* un-stacked**
   (`mtp.layers.0.mlp.experts.{N}.{gate,up,down}_proj.weight`). The un-stacking
   problem did not disappear; it moved from the body to the MTP head.

## Deliverables

One PR, four ordered and separable commit groups.

### D1 — text-only mq4 (qt44)

```
hipfire-quantize --input <ornith-1.5-35b-a3b> \
                 --output ornith-1.5-35b-a3b.mq4 --format mq4
```

Expected: arch 6 detected; canonical stacked-expert path; `shared_expert` and
`shared_expert_gate` carried through the existing named path
(`crates/hipfire-quantize/src/diagnostics.rs:2196` already names
`model.language_model.layers.5.mlp.shared_expert_gate.weight`); `mtp.*` and
`model.visual.*` skipped.

**Gate G1** — quantizer exits 0; the arch-detection banner reports arch 6; the
skipped-param count equals `mtp` + `visual`; the artifact loads with no
`tensor not found`.

> **Trap.** Do not pipe the quant log through `tail -N`. It drops the early
> arch-detection banner, which is the only evidence that arch 6 was chosen.
> Capture the full log.

The expectation that D1 needs zero code change is **planned, not established**.
D1 runs first precisely so that D2–D4 are written against a known result.

**Measured 2026-08-20. Three findings that revise this section.**

1. **D1 did need a code change — a pre-existing regression, not an Ornith
   issue.** `hipfire-quantize` panicked at `pipeline.rs:3806`, *index out of
   bounds: the len is 1 but the index is 1*. Root cause: commit `d1d172e9c`
   ("decompose quantize run(), 5,372 → 2,441 lines, **byte-identical output**")
   extracted `handle_moe_expert_3d` and replaced `if is_moe_expert_3d { … }`
   with a bare block, leaving the predicate computed and discarded — the file
   contained exactly one reference to it. The function indexes `shape[1..][1]`
   unconditionally, so any 2-D tensor named `*experts.gate_up_proj` /
   `*experts.down_proj` panics. It stayed latent because models with only
   stacked-3D experts never present one; Ornith 1.5's MTP module does.
   **The regression lives in `feat/ternary-bonsai-27b` (PR #597)**, is inherited
   by #599, and is **not** on master — no shipped quantizer is affected. Fixed
   here to unblock, and flagged for the stack owner, who may prefer to move the
   fix down to #597.

2. **Runtime is ~6 minutes, not hours.** The full 35B quant completes in about
   six minutes on this box. Every schedule estimate in this document that
   assumed a multi-hour quant was wrong by two orders of magnitude.

3. **`Mean quant error: 0.00000000` is a reporting gap, not a measurement.**
   `total_quant_error` / `max_quant_error` are accumulated only on the Q8HFQ
   path (`pipeline.rs:4586`, `:5847`); the MQ4/qt44 path never touches them, so
   the summary prints zero regardless of actual error. **This line must never be
   cited as evidence of quantization fidelity.** Pre-existing and out of scope
   to fix here — the KLD work below is the actual quality measure, and this is
   precisely why it exists.

### D2 — MTP sidecar

`mtp_extract` over `mtp.*`. Its known-name table currently addresses
`mtp.layers.0.mlp.shared_expert.*`
(`crates/hipfire-quantize/src/bin/mtp_extract.rs:351-369`); whether it handles
**un-stacked routed experts** is unverified and is the first thing D2
establishes. If it does not, port the body-side fusion: vstack gate-then-up into
`[2·inter, hidden]`.

**Format asymmetry to resolve in D2.** `mtp_extract`'s packer emits
`QuantType::MQ4G256` — the *historical qt13* — via `quantize_mq4g256`
(`crates/hipfire-quantize/src/bin/mtp_extract.rs`, `QuantChoice::Mq4` arm). It
has no qt44 path. So a sidecar built today is qt13 while the trunk is qt44.
D2 must either confirm the loader accepts that trunk/sidecar mix or extend
`mtp_extract` to qt44. This is stated as an open question, not a decision.

> **Order is load-bearing.** The consumer computes
> `silu(gu[:inter]) * gu[inter:]`. Emitting up-then-gate is a silent lobotomy
> that produces a loadable, plausible-looking, wrong model. The coherence gate
> is what catches it.

**Gate G2 — run first, before any D2 implementation work.** Dump every learnable
RMSNorm weight in the `mtp.*` module and assert they are not uniformly exactly
1.0 with std 0.

Rationale: this is the exact failure mode that produced τ=0.00 on ORNITH 1.0's
DSpark drafter. That checkpoint shipped trained matmuls (`q_proj`/`fc`/`lm_head`
std ≈ 0.02) alongside completely untrained norms (every RMSNorm exactly 1.0,
std 0.0), against a working reference whose norms measured mean 1.52 / std 0.14.
Days were spent proving hipfire's drafter math correct — it was, to cosine
0.999873 — before the checkpoint itself was identified as the defect.

**If G2 fails, D2 is dropped from scope and reported as an upstream checkpoint
defect. It is not debugged.** No engine change can compensate for absent norm
scaling.

### D3 — vision tower

`--include-vision` over the 333 `model.visual.*` tensors.
`hipfire-arch-qwen35-vl` is marked `production` and claims "arch_id 5/6 + vision
tower". Ornith's tower has no deepstack, which is the simpler configuration.

**Pre-check before quantizing with vision:** confirm the crate's
`DEFAULT_MROPE_SECTION` (`crates/hipfire-arch-qwen35-vl/src/mrope.rs`) matches
`[11,11,10]` and that `mrope_interleaved: true` is handled. A mismatch here
degrades quietly rather than failing.

**Gate G3** — a real image through `generate_vl` yields a description relevant to
that image.

### D4 — publish

Ordering is not stylistic; the registry refresh is fail-closed.

1. Create the HF repo `hipfire-models/hipfire-ornith-1.5-35b-a3b` (lowercase
   canonical). **A human must do this** — the fine-grained token carries only
   per-repo scopes with `global: []` and 403s on org repo creation.
2. Upload with `hf upload-large-folder`, hardlinking artifacts into a staging
   dir on the same filesystem. Plain `hf upload` **hangs silently** on multi-GB
   files — observed stalling mid-transfer with the socket ESTABLISHED, byte
   counters frozen, and no error raised.
3. Teach `scripts/registry_gen.py`'s `arch_id_for()` the **new `ornith` tag
   family**. An unknown family returns `None` and hard-fails the entire daily
   run.
4. Only then add the curated `registry/models.json` entry (this is
   `CURATED_PATH` at `scripts/registry_gen.py:171` — *not* `cli/registry.json`,
   which does not exist on this branch). Tag `ornith1.5:35b-a3b`, mirroring the
   existing `qwen3.5:35b-a3b` entry. `size_gb` must match HF's byte count
   within `SIZE_TOLERANCE = 0.25`. `.mq4` is already in `KNOWN_QUANTS`.
5. Verify with `hipfire registry verify registry/v1.json`.

> `registry/v1.json` is **generated — never hand-edited**. And `hipfire run
> ornith…` will not resolve before merge: the CLI reads a published cache
> (`~/.hipfire/registry.cache.json`), not the in-repo file. Failure to resolve
> pre-merge is expected and is not evidence of a broken entry.

## Validation

### Coherence

A 5-genre battery modelled on `scripts/coherence-gate-qwen35-dspark.sh`: greedy,
Q8 KV, `empty=0`, `attractor=0`, decoded text inspected rather than only
counted. Ornith is a thinking model, so prompts use `/no_think`, as the 1.0 gate
did.

### KLD

Via #599's `saddle-quant`, corpus `bartowski_v5`.

**RESOLVED 2026-08-20 — a high-precision oracle is NOT constructible for this
model, and the reason is structural rather than a resource limit.**

Two independent walls:

1. **RAM.** Measured 125 GB total, 73 GB available. F32 weights for 34.66 B
   params are 139 GB and BF16 are 69 GB — the latter fits the weights only, with
   nothing left for activations or KV.
2. **The quantizer cannot emit high-precision MoE experts at all.**
   `handle_moe_expert_3d` can emit at most 6-bit for routed experts
   (`MQ6G256`/`HFQ6G256`); there is no Q8 and no F32 expert path. `--format
   q8f16` therefore produces an artifact whose 20,480 routed-expert tensors are
   still **4-bit qt13** — measured at 4.55 bits/weight overall. Using it as a
   reference would have measured qt44-against-qt13 and understated error badly.
   It was built, inspected, and discarded.

Consequence: the best available reference is a **6-bit oracle**, only two bits
above the 4-bit candidate. A KLD figure against it is a **lower bound on true
quantization error**, not a quality claim, and is **not comparable to #599's
arms**, which used a different oracle. Its legitimate use is regression
detection — a decode-level defect of the kind #599 hit (WT2 KLD 12.14 against a
0.044 baseline) would be glaring even against a 6-bit teacher.

Any figure this branch publishes must carry that framing. The original text
below is retained for the reasoning that led here.

**Oracle feasibility is an open question with a concrete number.**
`build_kld_ref_native` is documented against an **F32 oracle** (`--format f32`
/ `oracle`, all weights widened to F32). For a 35B model that is roughly
**140 GB of weights** — larger than this box's 128 GB of unified memory. An F32
oracle is therefore probably not runnable here. The fallback is a lower-precision
oracle (BF16 ≈ 70 GB, Q8 ≈ 37 GB), which changes what the KLD *means*: it
becomes quant-vs-Q8, not quant-vs-oracle. If we take that fallback, the oracle
precision is recorded in `OracleStats` and every reported figure is qualified
accordingly. An unqualified KLD number is not an acceptable output of this work.

The teacher is validated and its `OracleStats` **stored in the reference
header**, not printed. That crate exists because the previous pipeline let a
BF16 passthrough score PPL 1392 on WikiText-2 and still emit a structurally
valid reference. `n_chunk` is chosen by `min_chunks_for_power`, not inherited
from the old `n_chunk=24` that yielded overlapping CIs across five arms spanning
0.044–0.067. `WindowSpec` and both `ArtifactId` digests are recorded.

### Hardware limitation — to be stated in the PR body

This work is validated on **gfx1151** (Strix Halo, Radeon 8060S).

Superseded as of the MQ V2 release on `master`. When this was written, #599
admitted qt44/qt45 batched prefill only on gfx1200/gfx1201 and gfx11 took the
scalar per-token fallback, so this branch carried its own scalar gfx11 ports of
the dense gate_up/qkv/qkvza/residual GEMMs. `master` now ships WMMA
implementations of all four for gfx11 (`gemm_*_mq4g256v2_wmma_gfx11_bt`,
`*_gfx1100_mw_lds`), which are strictly better than the scalar ports. **Those
four kernels have been dropped from this branch**; the dense path is master's.

What remains unique here is the grouped **MoE** qt44 kernel
(`gemm_mq4g256v2_moe_grouped_wmma_k2`), which has no counterpart on `master` for
any `mq4g256v2` shape — without it a qt44 A3B MoE model fails prefill outright.

- **No performance number** produced by this branch is comparable to #599's
  gfx1201 figures, and none will be presented as such.

Correctness and coherence of the arch-6 path are what gfx1151 validation
establishes. That is the claim, and its limits are part of the claim.

## Out of scope

- Ornith 1.5 **9B** (arch 5, dense) and **397B**.
- A qt45 / MQ4C arm. Ornith-specific qt44-vs-qt13 A/B is likewise excluded; #599
  already establishes the format delta on its own arms.
- gfx1201 validation and any batched-prefill perf claim.

## Risks

| risk | handling |
|---|---|
| MTP checkpoint ships untrained norms (ORNITH 1.0 precedent) | G2 runs first and is cheap; on failure, drop D2 and report upstream — do not debug engine code |
| MTP routed experts un-stacked and `mtp_extract` cannot fuse | Port the body-side vstack; assert gate-then-up order; coherence gate is the detector |
| Vision mrope section/interleave mismatch | Pre-check against the crate before quantizing with `--include-vision`; degrades quietly otherwise |
| KLD teacher invalid or infeasible on 35B/gfx1151 | Validate teacher and store `OracleStats` before trusting any KLD number; if infeasible, report that rather than publishing an unbacked figure |
| #599 moves under this branch | Single branch; rebase; re-run the ownership audit |
| One PR spanning four concerns | Ordered separable commit groups; D1 lands before D2–D4 are written |
| Registry entry lands before upload completes | D4 ordering is mandatory — a referenced-but-absent file breaks the whole daily refresh, not just this row |
