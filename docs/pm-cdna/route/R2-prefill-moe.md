## Finding: no native-FP8 activation arm in gfx1201 routed MoE

**`HIPFIRE_IU4_PREFILL=0` does not put FP8 activations through Qwen4's routed-expert GEMMs.** It unlocks the separate dense MQ4v2 FP8 selector: `fp8_f2_row_active` explicitly requires `!iu4_prefill_enabled()`, exact gfx1201, symmetric MQ4v2, FP8-v2 enabled, no A8 route, no replay recording/capture, and the row/shape gates (`crates/rdna-compute/src/gemm.rs:10263-10275`). Routed gate/up instead selects symmetric **IU4**, F16 WMMA, or F32 SIMT; routed down selects symmetric IU4 or F32 SIMT on gfx1201 (`crates/hipfire-dispatch/src/pipeline/qt44_qt53_prefill.rs:1189-1245,1432-1506`). The grouped gfx12 kernel invokes **F16**, not FP8, WMMA (`kernels/src/gemm_mq4g256v2_moe_grouped_wmma.gfx12.hip:141-153`). Thus “native FP8 prefill” describes the eligible dense/trunk families, not this expert chain; even dense admission is conditional, not guaranteed by the env alone.

**The independent symmetric MoE arm can remain IU4 with `HIPFIRE_IU4_PREFILL=0`.** Its request predicate reads `HIPFIRE_QWEN4_MOE_SYM_IU4` and the frozen C2 compiler candidate set, not `iu4_prefill`; unset requests the arm on gfx1151/gfx1201 (`crates/rdna-compute/src/gemm.rs:46925-46935,47165-47189`). Dispatch additionally requires path 2, a source-verified symmetric route capability, the BF16 recipe, F32 input, and at least 512 routing rows (`crates/hipfire-dispatch/src/pipeline/qt44_qt53_prefill.rs:1017-1026`; `crates/rdna-compute/src/gemm.rs:354,46948,47180-47181`). It is not an FP8 arm: its PM builder uses `v_wmma_i32_16x16x32_iu4` on packed `block_i4_128` activations (`crates/peacemaker-isa/src/kernels/qwen4_moe_sym.rs:5-9`).

**Consequently the qt55 FP8×FP8 grouped MoE design below is a new generator arm, not an existing gfx1201 MoE arm port.** The parallel HIP implementation is currently weight-only: OCP FP8 weights → BF16 RNE, BF16 activations, BF16 MFMA, F32 outputs (`FP8:kernels/src/gemm_fp8b128_moe_grouped_bf16mfma.gfx942.hip:17-43,86-110`). Neither its filename nor qt55 implies FP8 activations. The 27B XTS gfx1201 KLD pin is not a Flash-Next MoE accuracy receipt (`PLAN:315-317`).

## Sealed lowering and geometry

- Policy capability fixes 512 experts, top10, hidden2560, intermediate640; routed gate/up must be QT44/MQ4G256V2 and down QT53/MQ4G128V2. Symmetry means every actual header passed `zp == -8*sc`, never inferred from dtype (`crates/hipfire-dispatch/src/families/moe.rs:103-115,137-170`). Architecture binding declares the symmetric policy only at rows≥512 (`crates/hipfire-arch-qwen4/src/gpu_forward.rs:537-541,786-791`). Sealed router consumes that capability and rounds logits/weights internally (`crates/hipfire-dispatch/src/pipeline/sealed_moe.rs:2095-2137`); specialized scratch validates before launch (`:2008-2012`; `qt44_qt53_prefill.rs:247-279`).
- `MOE_GROUPED_BLOCK_M=16` (`crates/hipfire-dispatch/src/families/moe.rs:30-31`). Flat slot is `token*10+rank`; gate/up gathers `flat/10`, down gathers `flat`. Each expert run pads independently to16; sorted padding and unused tile IDs are−1; `inverse_perm[flat]` restores actual row irrespective of scatter order (`kernels/src/qwen4_moe_scatter_stable_top10.hip:4-20,80-108`; `kernels/src/gemm_mq4g256v2_moe_grouped_wmma.gfx12.hip:47-87`). No host readback of live tile count is needed (`kernels/src/qwen4_moe_scatter_fused_k8.hip:55-58`).
- Router safety is independent of numerical policy: any NaN or infinity in a row invalidates all of that row's slots (`expert=-1`, `weight=+0`) and records a device-side router error. Every expert-ID consumer must check `0 <= expert < n_experts` before indexing, including PM images; an invalid inverse-permutation entry must not become a grouped-row address. The host reports the router error with layer and row at its synchronization/readback boundary and fails the request. Skipping invalid slots only contains the fault; it is not permission to return the remaining rows as a successful request. Finite rows retain the existing arithmetic, ordering and rounding.
- `tables/moe_table.rs` is **not the prefill dispatcher**: `BatchGt(1)` and WMMA grouped entries are documentation-only; dtype/env internal resolution is authoritative (`crates/hipfire-dispatch/src/tables/moe_table.rs:12-20,40-59`). Therefore adding an MFMA row only to this table does not implement a gfx942 sealed route.
- gfx1201 has `has_wmma=true` but `has_wmma_w32=false` (`crates/rdna-compute/src/arch_caps.rs:140-147`). Thus dispatch `gateup_bf16`, `gateup_silu`, and `down_wmma` do not take the gfx11 BF16-output/F16-down arms on gfx1201 (`qt44_qt53_prefill.rs:1066-1076,1167-1169`). Non-sym gfx1201 uses F32 grouped gate/up output, fused unscatter+rotation, and SIMT down. Do not list gfx11 `_bf16out`, `_silu_bf16out`, `_xf16`, or unscatter-BF16in as gfx1201 launches.
- For ≤8 rows path2 may use indexed down after grouped gate/up/unscatter (`qt44_qt53_prefill.rs:1396-1398,1465-1466,1513-1522,1574-1575`). `HIPFIRE_MOE_GROUPED_GEMM=0` also takes indexed gate/up/down. Proposed qt55 route refuses these distinct-order fallbacks and the CDNA atomic path0; one grouped kernel handles padded M1 as well as prefill.

## Proposed qt55 native-FP8 grouped tile contract

### Operands and numerical order

1. **Weights:** qt55 row-major codes `[E,R,K]`, then verbatim BF16 `s_inv[ceil(R/128),ceil(K/128)]`, expert stride round-up256. Gate/up R1280,K2560; gate rows0..639 and up640..1279. Down R2560,K640. Scale rows align because640%128=0 (`FP8:docs/quant-formats/fp8-e4m3.md:26-50`). Natural basis, no FWHT (`:15`). Read `s_w = f32(s_inv[(output_col/128)*(K/128)+kb])`; it is a **multiplier**, despite the name `s_inv`.
2. Preserve artifact bytes. Remap weight **exact byte0x80 to0x00 in operand registers** before FP8 MFMA, retaining signs of every nonzero byte. Reject OCP NaNs0x7f/0xff at artifact admission, not by pretending their FNUZ interpretation is valid (`FP8:docs/quant-formats/fp8-e4m3.md:100-110`). FNUZ has bias8,max240,NaN0x80,no−0 (`CDNA3 ISA §7.2 p.50`). Every admitted OCP weight code reads as `fn(q)/2` after zero remap (`FP8:docs/quant-formats/fp8-e4m3.md:86-98`). **This remap is value-exact, not signed-zero/BF16-bit identity**: the existing weight-only decoder explicitly restores−0 for teacher identity (`FP8:...bf16mfma.gfx942.hip:20-27,86-98`). Do not edit stored qt55 bytes or apply the remap to the teacher decoder.
3. Activations: recipe-boundary input in natural coordinates. Per whole row `a=2^clamp(ceil(log2(amax/224)),-31,9)`, zero row→1, as source (`kernels/src/mq4v2_fp8_producer_pack.hip:70-78`). Pack RNE with `v_cvt_pk_fp8_f32((x/a)*0.5)`, canonical zero, little-endian bytes. When `abs(x/a)≤224`, finite nonzero codes match the OCP producer's code grid because argument≤112; each hardware activation decodes to `fn(code)/2` (`PLAN:315-316`; `CDNA3 ISA §7.2 p.50-51`). No stochastic conversion.
4. For every output keep two F32 vectors: `total=+0`, and `partial=+0` reset at **each128-K block**. For kb=0..K/128−1, issue four MFMA K32 instructions at k=`128*kb+32*t`, t=0,1,2,3. Then for each output use a pinned DAG `scale = ((4.0f*a_row)*s_w)` and `total=fma(partial,scale,total)`; never carry the unscaled accumulator into the next block. Scale location is perblock, **not one final epilogue multiply**, because `s_w` changes withkb (`PLAN:316`). No split-K, no atomics, no row-count-specific K order. Fourfold decode compensation is exact as a power-of-two fold; total rounding/output equality to WMMA is **not** promised.
5. Gate/up stores F32 `[P,1280]`; unscatter combines gate and up only after both complete. For the existing MQ4 boundary, g/u and final product are BF16 rounded but SiLU itself is not (`kernels/src/moe_gate_up_unscatter_silu_top10.hip:49-55`). For the stock-FP8 teacher-compatible activation recipe, use the parallel natural-basis twin's extra `BF16(silu(g))` before `BF16(s*u)` (`FP8:kernels/src/fp8b128_moe_unscatter_silu.gfx942.hip:12-21,62-65`). The native FP8 GEMMs are generator-only whichever recipe is chosen; keep one explicit recipe, never let PM/HIP select different boundaries. Pack down rows afresh atK640. Down stores F32 `[P,2560]`; existing F32-source combine BF16-rounds per-expert output, weight, product and each expert-ID-ordered sum (`kernels/src/moe_down_combine_grouped_top10.hip:43-75`).
6. This differs from the BF16 teacher even beyond activation quantization: native FP8 multiplies raw FP8 weights then block-scale-adds, whereas weight-only baseline rounds each `fn(q)*s_w` to BF16 before BF16 MFMA (`FP8:docs/quant-formats/fp8-e4m3.md:67-79`; `FP8:...bf16mfma.gfx942.hip:20-32`). Keep independent accuracy/identity evidence; no claim that the ×4 fold alone makes teacher logits identical.

### Wave/tile mapping (same PM and HIP)

Proposed conservative geometry: block256 = fourwave64; grid `(R/64, P/16,1)`, one16-token group per expert tile,64output columns/CTA. Full gate/up is **20CTAs ×64=1280** outputs per16-row M tile; down is **40CTAs ×64=2560**. These counts are derived from qt55 shapes, not new model geometry. Under padded descriptor `{e,row0,16,0}`, skip e<0 before any load/store; zero operands and write+0 for sorted rows−1.

Use transposed hardware multiplication exactly like the existing grouped BF16 twin: hardware A=weights[16output,32K], B=activations[32K,16slot], D=[16output,16slot]; logical output is transposed on store (`FP8:...bf16mfma.gfx942.hip:34-50`). For wavew, lane l, `n=l%16`, `s=l/16`, output_base=`64*blockIdx.x+16*w`:

- A pair bytesi=0..7: `W[e, output_base+n, 128*kb+32*t+8*s+i]`, zero-remapped.
- B pair bytesi: `Xq[xrow(n),128*kb+32*t+8*s+i]`; `xrow(n)=sorted[row0+n]/10` for gate/up, `sorted[row0+n]` for down; negative slot means zero. Both pairs are64-bit packed little-endian.
- Four result registers r=0..3 represent `D[4*s+r,n]`: store `Y[(row0+n)*R+output_base+4*s+r]`. All four apply the **same activation scale of token/slot n**, and weight scale of output_base's128-output block. A16-output wave and64-output CTA never straddle a128-output scale row.
- Mapping follows `CDNA3 ISA §7.1.4 p.46-48`; actual opcode is `v_mfma_f32_16x16x32_fp8_fp8` (`CDNA3 ISA §7.1 p.42`, §7.1.4 p.46-48). Reuse one entry/shape for M1, M2, M16 and large prefill by zero-padding to16, not a separate GEMV order.

### LDS, registers, waits

- Proposed LDS `unsigned xl[2][16][36]`: two128-K code buffers; each logical row128B+16B padding; **4608B**, plus16F32 row scales64B =4672B. No weight LDS: each wave owns its16weight rows and loads8bytes/lane/K32 directly, with next-block weights/scales prefetched into VGPRs. Codes don't need BF16 expansion. This adapts the current BF16 twin's padded row staging (`FP8:...bf16mfma.gfx942.hip:124-145`), not its exact68-dword BF16 row width.
- Within eachK128, threadtid stages row=`tid/16`, kbyte=`8*(tid%16)` (8bytes/thread). B pair read starts at LDS dword `[buffer][n][8*t+2*s]`. Pad16B changes the128B row stride; **not claimed conflict-free**. Bank occupancy/performance needs on-card measurement. Bounds/padding are fixed and independent of prompt row count. At least twoF32x4 accumulator vectors/wave (partial,total) and operand/prefetch pairs; budget final register allocation against CDNA's unified512 VGPR/AGPR pool, not RDNA wave32 assumptions (`CDNA3 ISA §3.6.4 p.12-13`; existing architecture metadata must use64-bit EXEC/VCC).
- PM: wait VMEM before consuming fetched weight/activation registers; wait LDS stores before a cross-wave barrier/read, wait LDS reads before MFMA; barrier before buffer reuse. Use gfx9 `s_waitcnt`: VMEM loads **and stores** count/return in issue order, SMEM may return out-of-order, LDS in order; barrier is workgroup arrival, not a memory-counter drain (`CDNA3 ISA §4.3–4.4 p.19-20`). No gfx12 `vscnt`/wait instructions. HIP twin uses equivalent staging barriers and compiler-generated waits with the same dataflow.
- No `v_permlane16/x16` in gfx942 twins; width32 software subgroup work uses ds_bpermute and subgroup masks. F32→FP8 conversion partial-destination hazards need an intervening instruction/NOP between writes to the same packed register (`CDNA3 ISA §7.2 p.51`). **ISA correction:** packed conversion ignores instruction `clamp`; saturation overflow is controlled by `FP16_OVFL`, and SH_MEM_CONFIG bit8 is required (`CDNA3 ISA §7.2 p.50-52`). The bounded≤112 producer does not rely on overflow saturation.

## Portable / twin / blocked summary

- **Portable algorithm/source candidates on wave64:** incumbent router's explicit width32 fallback; integer fused scatter's non-gfx1151 serial prefix; elementwise natural unscatter; F32/BF16-source combine and order kernels. These contain no FP8 numerical interpretation. Stable scatter is algorithm-portable but source-tree arch guard needs an admitted gfx942 twin (parallel tree is the available implementation). No hardware certification is implied by CPU reading.
- **Needs a twin:** gfx1201 fast router (unsupported permlanex16, logical32 `__any`); O4/O8 reductions (unsupported permlanex16), WMMA expert tiles; guarded IU4 producers; every PM `.hxaco` bundle. The qt55 **FP8 activation producer and FP8×FP8 MFMA grouped GEMM do not yet exist in this source tree**. Existing parallel BF16-MFMA qt55 kernel is a baseline/interface reference, not an FP8-activation implementation.
- **Blocked from silent reuse:** gfx1201 PM binary on gfx942; int4 WMMA→nonexistent int4 MFMA; qt44/QT53 affine weight decoder applied toqt55; MQ rotated input for natural qt55 weights; generic CDNA atomic down_path0 or indexed few-row fallback for fixed-order qt55; teacher/capture use of native FP8 generator arm; unproved peer EP/compact-scratch/staging inheritance.
