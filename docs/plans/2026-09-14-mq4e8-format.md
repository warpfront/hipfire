# MQ4E8 — zero-correction 4-bit weight format for tensor-unit prefill

**Status:** **Dead — killed by the §4 quality gate on 2026-09-14.** Step 1 was
built (local branch `mq4e8-format` @ `c20e44ecf`, unpushed; quantizer,
qt=52 register row, lossless qt=44 re-emission for eval) and the WT2 ladder
run on the qt=44 recipe: G256 KLD 0.0939 (4.03 bpw), G128 0.0869 (4.07 bpw)
versus the MQ4v2 base reference 0.0404 in the same build and MQ4v1 0.0438.
2.1× over the gate and worse than v1; G128 vs G256 only +7%, so the loss is
the power-of-two group step (§7 risk 1: within a row, group scales are
constrained to 2^k ratios, average ~1.4× step overshoot → ~2× MSE), not
group coarseness. Two further findings retire the premise itself: the gfx1201
fp8 *dense* roof is ~191 TFLOPS (341 below is the sparse figure), so PR #757
already runs at ~49% of roof, and halving/removing its boundary correction
measured +0.1% (RM1) — the correction this format deletes is not the limiter.
Retained for the record; do not restart without a new scale encoding.

## 1. Why

The FP8-WMMA MQ4v2 prefill GEMMs (PR #757) run at **28% of the gfx1201 fp8
WMMA roof** (94.6 TFLOPS of 341 at N=384, gate_up 2×17408×5120). Every
geometry experiment that shared X across more rows or staged X in LDS was
bit-exact and *slower* (4-slab −50%, LDS-X −11…−45%), with WMMA count and
bytes moved identical. The wave is VALU-issue-bound, and the VALU is spent on
one thing: MQ4v2 carries **two (scale, zero) pairs per 256-K group**, so the
accumulator must be corrected at every 128-K half boundary —

    acc *= s_prev / s_new            (16 shuffles + 8·BV mul per slab)
    acc += (z_h / s_h) · Σ_half(x)   (8·BV fma per slab + the pre-pass sums)

— 40 corrections per wave at K=5120. On gfx11 (iu8 WMMA, i32 accumulators)
the same correction is worse: an i32 accumulator cannot be rescaled in place,
forcing a second accumulator set per half (the reason earlier fp8/iu8
attempts washed).

A format whose per-group scale is a **power of two** and whose codes are
**symmetric** removes both terms: the scale folds into the fp8/int8 operand's
exponent, and there is no zero-point term at all. The inner loop becomes
nibble→operand (one `v_perm` table, rebuilt once per group) and WMMA. That
is the only remaining lever on the GEMM side; expected effect is 28% → 50–60%
of roof (≈1.8–2× on the 60% of prefill that is GEMM), and it is the
precondition for the vLLM-style batched-prefill gains (N=4096 chunks only pay
when the kernel is compute-bound).

## 2. Format

Cross of MQ4v2 (quantizer) and MFP4G32E8 (scaling contract):

| axis | MQ4v2 (today) | MFP4G32E8 | **MQ4E8** |
|---|---|---|---|
| rotation | FWHT-256, seeds 42/1042 | none | **same as MQ4v2** |
| codes | uint4 0..15, affine | e2m1 | **int4 symmetric, q−8 ∈ −8..7** |
| group scale | fp16 per 128-K half | e8m0 per 32 | **e8m0 per group (G ∈ {256,128,64})** |
| row scale | none | none | **fp16 per output row** |
| zero-point | fp16 per half | none | **none** |
| bpw @G256 | 4.25 | 4.25 | **4.03 + 16/K** |

Dequant: `w = 2^e_g · s_row · (q − 8)`.

Group layout (G=256): 1 byte e8m0 + 128 B nibbles = 129 B; pad to 132 B
(4-byte aligned) so the loader's stride assumptions survive; per-row fp16
scale in a sidecar vector `[m]` like the MFPE8 row tables. G=128 → 66 B,
G=64 → 34 B (same 34-B stride as Q8_0, convenient).

Quantizer: rotate as MQ4v2 does; per row compute `s_row = absmax(row)/…`
(or the Lloyd-style search already in `hipfire-quantize`); per group pick
`e_g = ceil(log2(absmax_g / (7.5·s_row)))` and round codes; optionally
one refinement pass on `s_row` given the chosen exponents (cheap, data-free).
AWQ sidecar scales apply exactly as for MQ4v2 (they act on X, not W).

## 3. Kernels

* **Prefill fp8 WMMA (gfx12):** clone of `gemm_gate_up_mq4g256v2_wmma_fp8.gfx12.hip`
  minus the half-boundary block and minus `X_half_sums`. Per group: read
  `e_g`, build the 16-entry e4m3 table for `(q−8)·2^e_g` (four dwords —
  every value is exact in e4m3 while `e_g` keeps the magnitudes ≤ 448; the
  quantizer must clamp `e_g` into e4m3's range, which is always true when
  `s_row` absorbs the row magnitude), decode with `v_perm`, WMMA. The
  accumulator is in units of `s_row`; the epilogue multiplies by
  `s_row · an` (an = the existing pow2 X row scale). Pre-pass shrinks to the
  fp8 cast only. Three ABI modes and bt/slab variants carry over unchanged.
* **Prefill iu8 WMMA (gfx11/11.5):** same kernel with `wmma_i32_16x16x16_iu8`;
  the i32 accumulator never needs rescaling, one conversion at the end.
  This is the RDNA3 port that was on hold.
* **Decode GEMV:** MQ4v2 GEMV family with the affine replaced by
  `(q−8)·2^e_g·s_row` — fewer ops than today.
* **DFlash verify / MoE grouped:** same substitution; do gate_up/residual/
  qkvza first, everything else after the quality gate.

## 4. Quality gate (go/no-go, before any kernel beyond a parity oracle)

1. Quantize Qwen3.8-27B to MQ4E8 at G256, G128, G64 (same imatrix/AWQ
   recipe as the qt=44 artifact, `2026-08-18…kld-beats-v1` §Fixture).
2. WT2 + v6 KLD via `eval_hipfire --max-chunks 24 --kv-mode q8 --kv-v q8
   --scoring-mode prefill` on a *CPU/F16 reference dequant path* (no new
   GPU kernel needed: dequantize to F16 at load and run the existing F16
   prefill), against MQ4v2 qt=44 = 0.039033 and MQ4v1 = 0.043776.
3. Accept if the best G is ≤ 0.041 at ≤ 4.15 bpw. Expectation: G256 lands
   between v1 and v2; G128 recovers v2. If none does, stop — the format is
   dead and the prefill lever is a quantizer-side problem, not a kernel one.

## 5. Perf gate

Kernel: fp8 MQ4E8 gate_up ≥ 150 TFLOPS at N=384 (≈45% of roof; the 2×
target over today's 94.6). Model: `hipfire bench --matrix --pp 512,2048,8192`
with the #757/#758 flags: pp512 ≥ 2000 single card. Decode must not regress
(GEMV is strictly simpler; expect ≥ parity).

## 6. Scope and order

1. Quantizer + loader dtype `MQ4E8G256` (+G128/G64 as the same dtype with a
   group-size field) + F16-dequant load path → KLD ladder (§4). ~1 day.
2. fp8 prefill kernel family (gate_up, residual, qkvza, qkv) + oracle vs the
   F16 path → §5 kernel gate. ~1 day.
3. Decode GEMV family + DFlash verify → `serve_harness battery`. ~1 day.
4. gfx11 iu8 variant (RDNA3/3.5 trickle-down). ~1 day, after 2.

Not in scope: MoE experts (Ornith) until the dense ladder is green; MFP
formats are unaffected; MQ4v2 remains the production format until MQ4E8
passes §4 and §5 and a serve battery.

## 7. Risks

* Pow2 group step costs up to √2 in step size before the row scale
  absorbs it; the FWHT-Gaussian argument says this is small, the KLD
  ladder decides.
* Symmetric codes waste one level (−8) unless the quantizer uses it;
  use the full −8..7 range with `absmax` mapped to 7.5.
* e4m3 table range: `(q−8)·2^e_g` must stay ≤ 448 and ≥ 2^−6 for
  exactness; the quantizer clamps `e_g` and the row scale takes the rest.
  Verify exactness in the oracle for every `e_g` in the artifact.
* Not ROCmFP4, not MXFP4: those keep non-pow2 or per-16/32 fp8 scales and
  still pay a rescale every 16–32 K.
