## 2. Exact arithmetic and traffic model

All tile dimensions below are **M rows × N batch columns**. K is the contraction dimension; N=512 here. A group is136 B:128 B nibble payload plus two4-B half2 headers. One column/K128 Xq block is72 B. LDS A stride42 dwords includes eight replicated header slots and two unused padding dwords; those40 written words are not136 global bytes.

For positive full tiles `(Tm,Tn)`, define `G=K/256`:

- Unique A footprint: `M*G*136` bytes; logical launch A reads: `M*G*136*(N/Tn)`.
- Unique Xq footprint: `(K/128)*N*72` bytes; logical launch Xq reads: `(K/128)*N*72*(M/Tm)`.
- Grid: `[M/Tm,N/Tn,1]`; logical per-WG/group fill: `136*Tm + 144*Tn` bytes.
- A fill per output/group: `136/Tn`; Xq fill per output/group: `144/Tm` bytes.
- LDS: `4*(42*Tm+18*Tn)`; eight-wave running sums/lane: `Tm*Tn/256`.
- Arithmetic: `2*M*K*N = 91,268,055,040` dense integer operations for **each** production shape. Fold/output work is additional, not included in this TOPS numerator.

### 3.1 Wave, lane, sum and store mapping

Let `w=threadIdx.y∈[0,7]`, `lane=threadIdx.x∈[0,31]`, `r=lane%16`, `n∈{0,1}`, `c∈{0,1,2,3}`, `l∈[0,7]`:

```
row0 = 64*blockIdx.x;        col0 = 256*blockIdx.y;
wave_row = 32*(w/4);         wave_col = 64*(w%4);
i = wave_row + 16*n + 2*l + lane/16;
j = wave_col + 16*c + lane%16;
sum_index = (2*c+n)*8+l;
Y_index = (col0+j)*M + (row0+i);
```

Each wave owns a contiguous32×64 rectangle; waves0–3 own rows0–31 and waves4–7 rows32–63, with four distinct64-column bands. Each owns8 independent16×16 subtiles, exactly like shipping’s count, and each lane owns `sum[64]`. Different wave/output assignment is allowed; each **output’s arithmetic history** is not allowed to change. Set overwrites exactly once; add reads old Y once and performs the existing final addition once, after all K groups. There are no cross-WG reductions or output races.

Planner CPU enumeration verified all16,384 outputs are owned exactly once by these formulas. That is a mapping proof, not a GPU numerical result.

### 3.2 Per-output arithmetic and bounded A-fragment reuse

For each kb increasing from0 toK/256−1, process h0 completely, then h1 completely. For each fixed n, keep four `int32x8_t` accumulators `acc0..acc3`, one for each c, initialized to zero. This is four **different-output chains**, not four partial sums of one output. For t=0..3 in increasing order:

```
ap = tile_x + (wave_row+16*n+r)*42 + 16*h + 4*t;
bp(c) = tile_y + (wave_col+16*c+r)*18 + 2 + 4*t;
```

Load av0 from ap+0 and av1 from ap+2 once for the current t, then reuse that same A pair for c0,c1,c2,c3. Load B pairs just-in-time for one c rather than retaining four full B pairs across the loop. Each acc receives, in exactly this order:

1. `wmma(false,av0,true,bv0,acc,false)` for K offsets32*t..32*t+15;
2. `wmma(false,av1,true,bv1,acc,false)` for offsets32*t+16..32*t+31.

There remain8 K16 WMMAs into **one acc per output subtile per half**, then exactly one W4.0-pinned fold per output. The integer absolute bound is15,360 per128-term dot, but overflow freedom is not permission to reorder it. ### 4.2 Bank check: no new stride, but no assumed bandwidth result

The Xq **column stride remains18 dwords**, not256; only the number of columns and wave-column bases change. Under the gfx11 32-bank/4-B address model, a B b64 read starts at bank

`(18*(wave_col+16*c+r) + 2 + 4*t + {0,2}) mod32`.

`18*wave_col` and `18*16*c` are multiples of32. Since gcd(18,32)=2, r0..15 visits all16 even start banks; each b64’s second word covers the corresponding odd bank. Lanes r and r+16 request identical addresses as shipping. A b64 addresses likewise use stride42 with gcd(42,32)=2; the new A base4,608 dwords is bank-phase0, as was the old2,304-dword base. Scalar Xq d/s reads preserve the same distinct-address bank pattern. Header replication and output-lane map are retained.

Planner CPU enumeration verified these bank-address permutations for the scalar/b64 model. **This does not prove conflict-free execution:** inspect actual `ds_read_b64`/combined-vector instructions, service groups, duplicate-address broadcast behavior and issued LDS traffic. Sequential c bases all share bank phase, so additional in-flight requests can still contend for throughput even with good individual-instruction addresses. Full-tile consumer B-read count is not doubled merely by having256 columns; the eight-subtile/wave count is unchanged. The doubled **global/L2 Xq fill and LDS writes** are separate from consumer reads.

A payload lanes still span128 adjacent bytes, but the payload begins at gp+8 and136-B groups can straddle cache transactions. Rows are separated by the full packed K-row stride, not contiguous136-B groups across M. At64 rows each wave has half as many row-fill iterations, potentially reducing load ILP; metadata uses half the waves. Inspect actual transaction/coalescing behavior rather than claiming half the memory instructions means half the latency.

### 4.3 Exact per-group state machine

A and Xq are immutable global inputs owned by the caller/scratch producer. Each WG exclusively owns its LDS and output rectangle. Each lane exclusively owns its64 FP32 sums. All256 threads participate in all four barriers; no producer-only role or asynchronous overlap is introduced.

| Transition | Before / allowed writers | Required action | After / invariant |
|---|---|---|---|
| Entry→fill kb0 | Y unchanged; sums initialized+0; LDS arbitrary | Disjoint A and Xq0 writers fill all consumed cells | Consumers cannot run before B0 |
| B0 publish | A(kb) and Xq(2kb) stores issued | `__syncthreads()` | All waves may read complete A and Xq0; no LDS writers during dot/fold0 |
| dot/fold0→B1 release | Each output has completed all earlier groups | Eight ordered WMMAs/output, pinned fold h0; `__syncthreads()` | All Xq0 reads are finished; Xq plane may be overwritten; A remains immutable |
| Xq1 fill→B2 publish | Xq plane exclusively owned by disjoint fill writers | Fill Xq(2kb+1), then `__syncthreads()` | Complete Xq1 visible; same A(kb) still visible |
| dot/fold1→B3 release | Each output’s current h0 already accumulated | Eight ordered WMMAs/output, pinned fold h1; `__syncthreads()` | Every read of this group’s A/Xq finished; sums contain complete groups0..kb |
| B3→next group | LDS is reusable; sums private | Advance kb by1 and refill, or enter epilogue | No stale LDS group/half can be consumed |
| Epilogue→return | Complete sums; one owner/output | Existing set or one final residual add at Y_index | Exactly the admitted output rectangle changed; inputs unchanged |

K%256==0 and K>0 make both halves present; retaining a redundant uniform half guard is harmless, but removing a workgroup barrier is not authorized. No kernel-side transaction commits persistent KV, recurrent, convolution, scratch generation, graph, or replay state. On launch failure, propagate the existing error; partial Y writes are not promised rollback.

## 9. Risks and planning proof

1. **Dominant risk: Xq cost replaces A cost.** Approximately200.54 MB more logical Xq reads/launch plus extra LDS fill writes may overwhelm94.70 MB fewer A reads, especially if L2 hit/service behavior changes. A0’s combined-fill bound cannot resolve this. Both isolated and in-model timing veto the idea.
2. **Register cliff.** Four column accumulators plus sum64 and unrolled fold temporaries can cross192 or spill despite the same output count. W3’s188-VGPR2×2 bundle is not W4’s1×4 measurement. Read actual allocation and lifetimes; never budget by adding only named source arrays.
3. **LDS read/service behavior.** The18-dword stride and bank phase are unchanged, but256 columns, a different reuse distance and concurrent in-flight reads/writes can change service pressure. Address arithmetic is necessary, not sufficient evidence.
4. **A fill coalescing/ILP.** Same32-lane payload packets, fewer rows/wave and half-wave metadata participation can reduce latency hiding;136-B group alignment was never perfect. Measure rather than claiming coalescing improved.
5. **Floating-point contraction.** One-ulp drift can arise without changing integer K order. W4.0 must reproduce actual shipping ISA on both architectures, including running-sum accumulation; canonical source arithmetic is not enough.
6. **Finite-grid/warm-cache transfer.** Down has160 WGs rather than gate544, with68 rather than20 groups; both must pass. Hot-loop, profiled model and unprofiled throughput are separate environments.
7. **Route/retained metadata drift.** A correct raw kernel with128-based recorded grid or30-KiB layout paired to a wrong symbol is incorrect integration. Real graph/recorded-HIP replay and prepared-sidecar freshness are mandatory.
