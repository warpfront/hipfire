Date: 2026-09-15. Plan of record for composition, **not an admission or a measured kernel result**. Worktree: `/home/kaden/ClaudeCode/warpfront/wt-lloyd`; all paths below are absolute unless explicitly relative to a GitHub repository. This planning assignment changed only this document. No source edit, build, formatter, linter, GPU program, kernel launch, or project-wide test was run. CPU address, register-reservation, and exact-integer algebra checks were executed; their limited evidence is in §7. Main owns admission; an independent reviewer owns the final technical veto.

**Decision:** build one exact-gfx11 lab candidate that keeps the shipping four-wave/KT32 FA2 schedule and replaces only QK with `__builtin_amdgcn_wmma_i32_16x16x16_iu8_w32`: the F4b pre-convert emits i8 Q plus one f32 scale per query/head row; K stays as stored i8 codes, with only its eight per-block f32 scales separated into a tiny LDS plane; PV stays f16. First land a QK-only arm (PV option (a)) so the measured K-side win and KLD cost precede any P/V change.

## 10-line summary

1. F5a (QK i8 + f16 PV) is the selected first arm: only the fill and QK phases change; online softmax, PV, causal ownership, and cache formats do not.
2. F5b (i8 P + i8 V) is enumerated and costed below, but it is strictly a second bounded arm because a P'-fragment-per-d-tile form costs ~1,024 multiply/convert operations per compute wave per 32-key tile while saving only ~512 V dequant elements per fill lane if work were evenly shared.
3. F5c (cache-format change to per-key V scales) is rejected: it changes persistent state/ABI and cannot dominate enough to justify that risk.
4. IU8 WMMA has the same 32-cycle AMD calculator cost as the existing f16 WMMA on gfx1151 (`matrix_calculator.py`), so the target win is removed Q/K conversion and halved fragment/operand bytes, not a faster WMMA opcode.
5. Conditional on the parent's fill fractions, F5a plausibly removes ~12–17% of FA2 time relative to F4a; no percentage is banked until the extended attribution oracle measures it.
6. If F4b ships at −41% relative to F4a, the same F5a fill reduction gives a *combined* F4b+F5 FA2 reduction of about 20.3–29.8% relative to F4a; the kill gate remains stricter and direct: <20% faster than F4a-shipping at L8192 after two bounded iterations.
7. The K/Q integer accumulator is exact for F5a: one 32-dim block's worst signed product is `32*127*128=520,192`; two such blocks before a scale fold stay below `2^21`; sixteen accumulations stay below `2^25`.
8. The unavoidable numerical change is i8 Q quantization (`absmax/127` per query/head row); fwht3 additionally needs centroid requantization into a fixed i8 LUT, whose measured CPU maximum centroid error is `0.0004925984252*|cnorm|`.
9. Biggest technical risk: row-absmax Q quantization and this fwht3 centroid requantization change score distributions enough to fail the KLD or human serve battery, especially at long context; biggest schedule risk is a dequant-load bottleneck or a new K B-fragment LDS bank pattern.
10. **Abandon criterion:** after two bounded iterations, the candidate does not pass the KLD/human gates, cannot keep zero spill/≤256 VGPR/two-workgroup LDS capacity, or is less than 20% faster than F4a-shipping at L8192.

## 2. gfx11 wave32 IU8 WMMA facts, with verification status

### 2.1 Frozen builtin contract

The exact clang builtin for the shipping wave32 kernels is:

```c
int32x8_t c = __builtin_amdgcn_wmma_i32_16x16x16_iu8_w32(
    true /* a_sign */, int32x4_t a,
    true /* b_sign */, int32x4_t b,
    int32x8_t c,
    false /* clamp */);
```

Grounded facts:

- Prototype: `_ExtVector<8, int>(_Constant bool, _ExtVector<4, int>, _Constant bool, _ExtVector<4, int>, _ExtVector<8, int>, _Constant bool)`; argument names `a_sign,a,b_sign,b,c,clamp`; target features `wmma-256b-insts,wavefrontsize32` (`llvm/llvm-project:clang/include/clang/Basic/BuiltinsAMDGPU.td`, `__builtin_amdgcn_wmma_i32_16x16x16_iu8_w32`, source lines 524-527 in the fetched revision).
- LLVM intrinsic flags: `%A_sign`, `%B_sign`, and `%clamp` are immediate booleans; `true` treats an operand as signed, `false` unsigned; `clamp=true` saturates on overflow instead of wrapping (`llvm/llvm-project:llvm/include/llvm/IR/IntrinsicsAMDGPU.td`, `AMDGPUWmmaIntrinsicIU`, lines 3077-3088 in the fetched revision; `int_amdgcn_wmma_i32_16x16x16_iu8`, line 3109).
- Documentation record: both A and B operands require replication on gfx11 (two copies in wave32); the builtin's IU8 A/B operands are 128-bit (`llvm/llvm-project:clang/include/clang/Basic/BuiltinsAMDGPUDocs.td`, `DocWMMAIU_16x16x16_GFX11`).
- Fragment sizes: A/B are `int32x4` (four VGPRs, 16 packed i8); C/D are `int32x8` in wave32. The f16 A/B operands are eight VGPRs, so i8 fragments are half the f16 fragment register width.
- Existing hipfire iu8 precedent: `mma_i8` calls the same builtin with both sign flags `true` and `clamp=true` in `/home/kaden/ClaudeCode/warpfront/wt-lloyd/kernels/src/gemm_mq4g256v2_residual_mmq.hip:318-319`; its comments document signed direct use and i32 headroom at `:327-331`.

For F5a, use `a_sign=true`, `b_sign=true`, `clamp=false`. Signedness is fixed by the existing exact-value probes and by hipfire's IU4 probe comment: signA false means unsigned, signB true means signed (`gemm_mq4g256v2_residual_mmq_iu4.gfx11.hip:23-26`). Clamp must remain false because the design proves no overflow and saturation would silently hide an invalid scale/operand. The IU4 probe's **accumulator map** is the same map used by shipping: `acc[j] = C[2*j+(lane>>4)][lane&15]`; its A/B nibble ordering proof does not automatically establish byte ordering for IU8, so F5.1 must run a new i8 A/B byte-order probe before composing the score path.

### 2.2 Rate and issue model: measured evidence required

The authoritative AMD GPUOpen WMMA article states that a WMMA instruction coordinates 32 clocks of optimal scheduling and that RDNA3's theoretical IU8 and FP16 rates are both 512 ops/clock/CU (`https://gpuopen.com/learn/wmma_on_rdna3/`). The AMD matrix instruction calculator's RDNA3 database gives both `v_wmma_f32_16x16x16_f16` and `v_wmma_i32_16x16x16_iu8` `cycles: 32` and opcode values 64 and 68 respectively (`ROCm/amd_matrix_instruction_calculator:matrix_calculator.py`, RDNA3 rows at lines 2302-2324 and 2390-2413 in the fetched revision). That database maps `gfx1151` to `rdna3`.

**Unverified here:** exact gfx1151 sustained issue throughput, WMMA-to-WMMA dependency bubbles, VALU co-issue behavior, VGPR cache/bank behavior, and the ISA PDF's exact encoding/modifier text. The reader could not retrieve the RDNA3 ISA PDF itself; these facts must be checked against the final compiled object's disassembly and a scoped timing probe before any claim uses a rate. F5 therefore predicts no WMMA issue-rate gain: IU8 is expected to be *not faster* than f16 per 16x16x16 step.

### 2.3 Reused IU4/MMQ idioms

Reuse these idioms, not their K/N geometry:

- accumulate a bounded integer dot in one i32 WMMA accumulator, then convert and fold once with real scales (`gemm_mq4g256v2_residual_mmq_iu4.gfx11.hip:162-213`);
- keep scale metadata separate from packed code payload (`load_iu4_tile` stores codes and headers separately, `:123-160`);
- stage no unnecessary expanded array; consume raw packed words directly when possible (`:121-160`);
- preserve the proven wave32 lane replication and duplicate-address simplification (`:23-29`);
- reject a silently wrapping accumulator by construction, not by relying on clamp.

Differences that must not be imported: F5's K scale varies every 32 dims, so the IU4 kernel's one fold per 128-K half is not sufficient. F5a must fold every 32-K block (two K16 WMMA steps) into an f32 score. Likewise, the existing iu8 MMQ fold has no causal/softmax state and cannot be copied as an attention state machine.

## 3. F5a QK design

### 3.1 Q quantization and ownership

Per row `(batch token q, head h)`, the F4b pre-convert computes:

- `absmax = max_d |Q[q,h,d]|` over the full D=256 row;
- `sQ = absmax / 127` as f32; if `absmax == 0`, use `sQ = 0` and all codes zero;
- `q8[d] = round_to_nearest_int(Q[q,h,d] / sQ)` clamped to [-127,127].

The exact integer-to-byte conversion is frozen by measurement in F5.1: test the target `v_cvt_pk_i8_i32`/compiler lowering and then hard-code the probe-verified rounding rule. Do not claim a particular round-half mode until that probe exists.

The natural place is the parent-frozen F4b pre-convert kernel, not the FA2 body. **Frozen F4b contract handed by Main and binding on both F4b and F5:** a new pre-convert kernel `attention_fa2_q_preconvert_gfx11` in `/home/kaden/ClaudeCode/warpfront/wt-lloyd/kernels/src/attention_q8_0_fa2_gqa.gfx11.hip` (same file, separate `__global__`) reads f32 Q rows `[batch,24,256]` and writes f16 scratch `[batch,24,256]` using the identical `(_Float16)` cast the body uses today; in fwht3 mode it performs the current `fwht_shfl_forward_256` rotation before the cast, so the FA2 body no longer mutates Q. The FA2 entries then take `const _Float16* q16` at kernarg offset 0 in place of `const float* q` (same slot, same size), and the fwht3 prologue is removed. Host launchers allocate/reuse the existing `fa2_q16_scratch` convention (`scratch.rs:198-203,518-535`).

F5 extends that same kernel with a separate lab mode symbol/mode, **not** by changing F4b's f16 scratch contract: it emits `[batch,24,256] i8` plus `[batch,24] f32` row scales into a new `fa2_q8_scratch` (padded row stride 260 bytes, `batch*24*260` bytes; 3,194,880 B at N512). The i8 body entries take `const unsigned char* q8` at offset 0. Under F5, fwht3 rotation happens in the pre-convert before i8 quantization, so the FA2 body reads immutable Q codes and remains replay-idempotent. F5 must sequence after F4b's landed edit to the shared kernel file; it must not race or rebase that file.

### 3.2 K payload and scale plane

For a 16-key subtile, the LDS K payload is raw i8 codes in key-major order: `16*256 = 4,096 B = 1,024 dwords`. Define the K code dword for key `k` and code dword `p=0..63` at:

```text
K8[k][(p + fa2_swiz(k & 15)) & 63]
```

`fa2_swiz` is unchanged. Because the row is 64 dwords, not 128, the mask changes from 127 to 63. For a K16 WMMA, the B fragment covers 16 K values: code dwords `4*dc + 0..3`. The A row is query row `ml`; lanes `ml` and `ml+16` supply identical rows, exactly as in the shipping duplicate-row contract.

For KT32, add one contiguous f32 scale region after the K/V planes:

```text
KS[k][b] = f32(f16 scale of Q8 K block b for key k), k=0..KT-1, b=0..7
```

This is 1 KiB at KT32. It is not part of the cache format and never survives the tile.

### 3.3 Exact score algebra and scale fold

For a query row `q`, key `k`, and K block `b`:

```text
C_b = sum_{d=32b..32b+31} q8[d] * k8[k,d]
S_ref[q,k] = scale_attn * sQ[q] * sum_b sK[k,b] * C_b
```

Per subtile the consumer uses two i32 accumulators, one per K16 step inside each 32-dim block. After every two K16 steps it folds:

```text
sacc_f32[j] += (float)C_i32[j] * (sQ * sK[k, b])
```

then zeros the integer accumulator. The existing even/odd key ownership remains: lane `(ml,half)` owns `S[query=ml][key=sub*16+2*j+half]`; `sK` for those two keys is read from the scale plane, broadcast naturally by the same lane pair. The subsequent mask/max/exp/m/l/P sequence is source-identical to shipping after score formation.

The exact bound is intentionally small: `|C_16| <= 16*127*128 = 260,096`; `|C_32| <= 520,192`; two K32 folds before reuse stay below `2^21`; sixteen folds stay below `2^25`. No clamp is needed and no i32 wrap is possible. A CPU scalar algebra check in §7 verified this factoring for random exact codes/scales and produced a negative control proving one post-hoc scale for all 256 dims is wrong.

### 3.4 fwht3-K fill path

fwht3's LUT is nonuniform: `TURBO_C3_256 = [-0.134860,-0.083320,-0.046469,-0.015176,+0.015176,+0.046469,+0.083320,+0.134860]`. It is not a signed fixed-point codebook. F5 freezes a centroid-requantized LUT:

```text
gamma = 0.134860 / 127
LUT8[c] = round(TURBO_C3_256[c] / gamma)
       = [-127,-78,-44,-14,14,44,78,127]
sK[k,b] = cnorm[k] * gamma
```

The fill unpacks 3-bit codes and indexes this immutable 8-entry LUT directly to bytes, with **no f16 value and no `cnorm*LUT` multiply per element**. It materializes the same `sK[k][b]` scale eight times per key, preserving the Q8 downstream scale-plane shape. CPU arithmetic measured max centroid error `0.0004925984252` before `cnorm`, attained at the ±0.083320 centroid. This is an added K error beyond i8 Q and must be reported separately in the numeric evidence.

Per-block absmax requantization of fwht3 is rejected for F5: it needs a centroid scan or four LUT variants and changes the fill from a lookup to a value-dependent scale search. The frozen LUT keeps the "cheap LUT" requirement.

### 3.5 Cooperative fill counts

At KT32, 128 threads:

- Q8 K codes: `KT*8=256` slots, two iterations per thread. Each slot reads one 34 B block and stores its 32 code bytes plus one f32 scale. Use a bounded `memcpy` for the 32 code bytes (`blk+2`) exactly as the existing unaligned pattern does; never over-read the 34 B record. Store the code payload as eight dwords under the 64-dword swizzle and store `sf` into `KS[k][b]`.
- fwht3 K: same 256-slot loop shape. Each slot unpacks its block's 24 packed bytes into 32 LUT bytes, stores eight code dwords, and stores `cnorm*gamma` into `KS[k][b]`.
- V fill is unchanged in F5a and remains the f16 transpose loop at `attention_q8_0_fa2_gqa.gfx11.hip:298-342`.

Keep the same two barriers per KT tile: publication after cooperative fill and retirement after all PV reads. Fill zeroes codes and scale for out-of-sequence records; causal masking remains score-side and never relies on zero K/V as a mask.

## 4. PV options and recommendation

### (a) f16 PV unchanged — selected first

V fill, P reconstruction, PV WMMA, O rescale, and epilogue are unchanged. Only K-side fill and QK are integerized. Cost: no new PV VALU; benefit: removes K dequant and halves Q/K operand traffic. This is the only option whose numeric delta is limited to Q quantization (plus fwht3 LUT requantization), so it is the mandatory first measurement.

### (b) i8 P with stored i8 V codes — second, only if F5a clears gates

Quantize probabilities per query row after the existing f32 `earr` computation: `pmax=max_j e_j` on each half plus the existing xor16 exchange, `sP=pmax/127`, `p8=round(e/sP)`. V remains cache codes; LDS V payload becomes i8 codes plus `sV[k,b]` scales. Fold each d-tile:

```text
Ofr[dc][j] += (float)C_i32[j] * (sP * sV[key, dc/32])
```

Per compute wave per 32-key tile, materializing one i8 P' fragment per d-tile costs `2 subtiles * 16 d-tiles * 8 lanes * 4 int32x4 words = 1,024` multiply/convert operations; the saved V dequant is `32 keys * 256 dims = 8,192` elements across the 128-thread workgroup, about 512 elements per fill lane if equally shared (64 elements per lane per key). This is not a clear win before considering extra scale loads, integer-to-float conversions, and register pressure. A P'-once plus transpose/broadcast variant can reduce the 1,024 figure, but it introduces a new P layout and lane-exchange risk. F5b must show a positive isolated timing delta and pass the full numeric gates; otherwise stop at F5a.

### (c) per-key V scale cache reformat — rejected

A per-key V scale would let PV fold one scale after a 16-key integer reduction, but it changes the persistent cache format, writer kernels, reader compatibility, state migration, and ABI. The measured parent attribution says PV WMMA is only 6.6–8.4% of FA2 and fill is 21.3–27.4%; a format migration cannot be justified by an unproven fraction of that tail. Explicit non-goal.

## 5. LDS budget and register model

### 5.1 Options

| Option | Dynamic LDS | Two-WG capacity | Verdict |
|---|---:|---:|---|
| KT32 single stage, K codes + f32 scales + unchanged V f16 | `32*(256+256) + 1024 = 17,408 B` | yes (`34,816 <= 65,536`) | **selected** |
| KT32 double-buffered codes/scales + current single V | `2*(8,192+1,024)+8,192 = 26,624 B` | yes | later schedule experiment only; no producer/consumer split in F5 |
| KT64 single stage | `64*512 + 2,048 = 34,816 B` | no (two WGs need 69,632 B) | reject |
| Two resident KT32 blocks plus double-buffered K | exceeds two-block LDS budget | no | reject |

The earlier rough 25.6 KB number counted double-buffered K codes plus one V plane and omitted the scale region; the selected first arm is simpler and smaller: **17,408 B**. It preserves two-workgroup LDS capacity with 30,720 B spare per CU. F5 does not introduce a second V plane or producer/consumer schedule; that was F3's shelved design and remains out of scope.

### 5.2 VGPR delta vs F4a at 255 allocated

F4a is parent-reported at 255 allocated VGPR. Treat this as a hard ceiling: F5 must be ≤256 allocated, zero spill, zero scratch. Design reservation per compute lane, reusing F3 §5 categories but with F5a fragments:

| Live category | F4a-ish reservation | F5a reservation | Delta |
|---|---:|---:|---:|
| O:16 float8 accumulators | 128 | 128 | 0 |
| f32 score fragment(s) | 8–16 | 16 (two subtiles) | 0 |
| i32 score accumulators, one 32-block pair live per subtile | 0 | 16 | +16 |
| P scratch `earr[8]` | 8 | 8 | 0 |
| m/l/alpha/max/sum temporaries | 8 | 8 | 0 |
| simultaneously live A/B operands | 16 (half16 K + half16 Q) | 8 (int32x4 K + int32x4 Q) | −8 |
| Q/K conversion/load temporaries | 8 | 4 | −4 |
| scale/predicate/address temporaries | 24 | 30 (adds sQ and two key scales) | +6 |
| allocation headroom | remainder to 255 | remainder | −10 net |

Net design delta is about **+10 VGPR** against the F3-style 256 reservation. Since F4a already sits at 255, the composer must recover ten registers by construction: zero each i32 accumulator immediately after its fold, avoid retaining both i32 pairs across softmax, scalarize scale/address temporaries, and keep the existing `asm volatile("" ::: "memory")` chunk boundaries only where needed. A spill or compiler allocation >256 rejects the arm. Metadata is checked before correctness or timing, using the resource rules in F3 §5.

## 6. Numeric and state gate (not bit-exact)

F5a is not bit-exact and must not pretend otherwise. The gate sequence is:

1. **Exact integer unit proof:** a host or scoped device probe compares `(i8 Q codes, raw K codes, sQ, sK)` against a scalar f32/f64 reference for random and adversarial rows. It must prove A/B byte order, duplicate lane behavior, accumulator map, no wrap, and exact fold identity for 16/17/31/32-key tails and masked rows.
2. **Fixture differential:** extend the attribution oracle so the candidate and shipping arm receive byte-identical K/V/positions and pre-F4b f32 Q; compare output max abs/relative error, RMS, finite/masked-row counts, and (for fwht3) immutable input Q bytes. F5a is expected to differ numerically, so no bitwise-eq requirement is imposed; all differences must be finite and explained by Q/K quantization.
3. **Model KLD:** run the pinned one-reference-chunk prefill fixture for shipping/F4a and F5a from identical fresh state on `qwen3.8-27b.mq4-xt`; decode HFKSEQ v2 (`mean KLD`, p99, mean NLL) rather than console rounding. Admission requires `abs(mean_KLD_F5a - mean_KLD_shipping_arm) <= 1e-3` on that fixture. The current shipping value supplied for this fixture is **0.053275**; the pass interval is therefore approximately `[0.052275, 0.054275]`, subject to Main confirming the pinned reference/model identity.
4. **fwht3 mode:** repeat the same gate with `--kv-mode fwht3 --kv-v q8`. Report the extra centroid-requantization error separately and do not average Q8 and fwht3 outcomes.
5. **Human serve battery:** run `scripts/serve_harness.py` battery for the accepted arm and have a human read coherence/runaway/empty output. A KLD pass does not substitute for the battery read.
6. **No state mutation:** K/V/positions/sign tables remain byte-identical; Q becomes immutable after F4b pre-convert; output has exactly one writer. Any cache-format or writer change is out of scope.

## 7. Planning evidence executed for this document

CPU-only checks were run; none is GPU evidence:

- Enumerated K code dwords for KT16/32/64: `k*64 + ((p+fa2_swiz(k&15))&63)` is a permutation of each plane.
- For every subtile, d-tile, and b64 fragment start pair `{0,2}` within the four-dword fragment, the 16 unique `ml` rows have 16 distinct even starts modulo 32 banks; the two dwords per b64 cover all 32 banks. Duplicate lanes `ml`/`ml+16` intentionally read identical addresses, as in shipping. Producer stores and real bank-service time were not measured.
- Exact integer algebra: random signed i8 Q/K codes and dyadic per-block scales pass the two-step fold identity; a negative control proves one 256-wide K scale cannot be used.
- Register/LDS arithmetic in §5 was recomputed; KT64 two-block residency is impossible at 64 KiB LDS/CU.
- fwht3 fixed LUT arithmetic: `gamma=0.00106188976378`, LUT `[-127,-78,-44,-14,14,44,78,127]`, max centroid error `0.0004925984252`.
- PV option (b) arithmetic: 1,024 added P' multiply/converts per compute wave per 32-key tile in the naive per-d-tile form versus about 512 V dequant elements saved per fill lane if work were evenly shared.

## 10. Risks and abandon criterion

| Risk | Why it matters | Gate/mitigation |
|---|---|---|
| i8 Q score precision at long context | Row absmax gives ~0.8% per-element max quantization before K scales; softmax exponentiates score errors and long contexts accumulate more candidates. | QK-only differential first; KLD ≤1e-3 absolute; long-L32768 fixture and human battery. |
| fwht3 centroid requantization | The LUT is nonuniform; fixed LUT adds up to `0.0004925984252*|cnorm|` centroid error, distinct from Q error. | Report separately; reject if fwht3 KLD/human output fails; do not silently switch to per-block scan without a new plan. |
| P quantization bias (F5b only) | P is in [0,1] after online max; per-row absmax quantization biases small probabilities and O. | F5b is optional and separately gated; never bundled into F5a admission. |
| Clamp/overflow semantics misunderstood | A wrapped score would be catastrophically wrong but may look like noise. | `clamp=false`; exact bounds `C32<=520,192`; F5.1 probe includes overflow-adjacent values. |
| New i8 K B-fragment bank pattern | 64-dword rows change modulo-bank residues versus the f16 128-dword row. | CPU enumeration passed read starts; inspect final DS loads and use one bounded swizzle adjustment if scoped timing shows a fill/read regression. |
| Fill becomes load/dequant bottleneck | K fill still touches the same global bytes; V f16 dequant remains. | F5a measures before F5b; no producer/consumer schedule inside F5; kill if <20% at L8192 after two bounded iterations. |
| Register pressure over F4a's 255 | Two i32 accumulators and scales add live state. | Net design delta +10 but hard cap ≤256; metadata check before correctness; reject spill/scratch. |
| F4b sequencing collision | Same kernel file is edited by both units. | F5.3 starts only after parent-accepted F4b; H's host wiring may prepare against the frozen contract but merges after F5.3. |
| Tooling evidence mismatch | LSP references were empty in this session; ISA PDF was not directly readable. | Source-search call inventory is recorded; composer repeats references with the correct worktree before exported-symbol edits; timing claims cite measured object/disassembly, not search output. |

**Abandon F5 immediately** if the F5.1 probe contradicts byte order/replication, the candidate cannot meet ≤256 VGPR/no-spill/17,408 B LDS, immutable-input or single-writer invariants break, KLD exceeds the 1e-3 absolute gate, the human battery fails, or two bounded iterations leave L8192 less than 20% faster than F4a-shipping. Do not convert the failure into a cache-format change, KT64, occupancy reduction, producer/consumer redesign, or P/V quantization by default.
