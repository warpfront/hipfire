# Plan B: lever space for 25 → 50 TOPS exact int8 GEMM (XDNA2 / AIE2P, Strix Halo) (historical planning)

> **Historical research note: superseded by the 0.4.2 serving route.** This file records an independent planning analysis (nothing built or run) of the lever space for 25 to 50 TOPS exact int8 GEMM from the 2026-10 NPU research cycle. It is not current guidance, and any figure in it is a dated fixture-bound measurement or an explicitly labelled historical estimate, not a product claim. The shipped 0.4.2 NPU route is the Flash-Next gfx1151 trunk input projection described in [npu-trunk.md](npu-trunk.md): `HIPFIRE_QWEN4_NPU_TRUNK=off|auto|on|emulate` (default `auto`, effectively `off` on every architecture except gfx1151), calibration schema 4, BF16-direct only. There is **no I32 serving contract** (no int32 partial, combine or fold exists in the product route). The out-projection program exists but is **not wired** into serving; `qsa.o` and the GDN o-projection are **not shipped**. Environment-variable names and flag syntax below are historical proposals or experiment switches, not supported configuration.

Planning only; nothing built, nothing run. Every magnitude below is an **estimate** unless it cites a `report.md` line. `path:line` refers to the NPU research workspace at `dc261e1`; `ref/…` is the reference corpus. ## 0. The denominators: three terms, each alone caps below 50

Useful ops: gate_up `2·4096·1280·2560 = 26.84 G`, down `13.42 G`. 50 TOPS = **0.537 ms** / **0.268 ms** per submit. Measured now: 25.36 → 1.058 ms, 23.93 → 0.561 ms (`report.md:436-437`).

| term | gate_up | down | source |
|---|---:|---:|---|
| MAC floor (1024 cycles/chunk, 1.80 GHz) | 0.546 ms = **49.15** (padded N=1536) | 0.228 ms = 59.0 | `gemm_core.rs:77-82`, `report.md:178` |
| issue schedule (1070/chunk) | 0.571 ms = 47.0 | 0.238 ms = 56.4 | `gemm_core.rs:11-13` |
| measured compute slope (1357/chunk, layout 0) | 0.724 ms = 37.1 | 0.302 ms = 44.5 | `report.md:416,420` |
| array data movement, DMA-only (`1470·chunks + 5800·waves`) | 0.86 ms = 31.2 eq. | V9 0.53 / V10 0.455 ms = 25.2 / 29.5 eq. | `report.md:442,450,457-460` |
| DDR, V9 bytes at the measured 55.4 R / 54.2 W GB/s | R 33.75 MiB → 0.64 ms = 42 | R 14.1 → 0.27, W 10 → 0.19 ms | `report.md:330,355,436-437` |
| **what 50 needs** | all-in ≤ 1006 cycles per padded chunk — **impossible**; needs no padding | ≤ 1208/chunk incl. per-wave share | arithmetic |

Consequences that frame every lever:
1. **gate_up at 50 is unreachable in the 512×512 wave geometry** (49.15 at the MAC floor with N padded 1280→1536). Padding removal is a precondition, not an optimisation (agrees with Plan A §3).
2. **Compute stalls alone cap at 44.5 (down) / 37.1 (gate_up)**: 1357 vs 1070 issue cycles. 50 needs ≤ ~1190 cycles per chunk all-in (Plan A's 1189.59/1144.72). The stall term must at least halve.
3. **Array-side delivery** is 8 KiB per core per chunk in 1470 cycles = 5.57 B/cycle/core (`report.md:459`); the core consumes 6.04 B/cycle at 1357 and would need 7.66 at issue rate. Whatever the DDR path does, the memtile→core delivery must rise ≥ 10 % even in the best geometry (§2 L4), or ~35 % at today's geometry. This is the term V10 exposed (DDR bytes removed, no speed-up, `report.md:457-460`).
4. **DDR** binds gate_up today (A read 3×) and down's C write (10 MiB irreducible int8). After the geometry lever both fall under the critical path *if* the port stays at ~55 GB/s; under GPU concurrency the port is shared (`report.md:469-475`).

Stream width is unknown and sizes the array term: the source models 4 B/AIE-cycle per channel (`gemm_array.rs:1511-1517`, `gemm_core.rs:66,1122`), but one shim channel measured 11.8 GB/s = 6.6 B per 1.80 GHz AIE cycle (`report.md:330`), above a 4 B/cycle link (the link's own clock is unknown; B per AIE cycle is the figure the design needs). If memtile→core links deliver ~8 B/AIE-cycle, 1470 cycles for 4 KiB is ~3× overhead (handshake/latency) and buffering levers pay. If they deliver 4 B/cycle, the two core S2MM channels give 8 B/cycle max: 7.66 required at issue rate is *under* that (Plan A is right that this does not forbid buffering), but it needs ~96 % sustained link utilisation at today's bytes/MAC and ~90 % after L4 — 50 becomes improbable rather than impossible, and byte-per-MAC reductions (L4, and L5 if ever allowed) carry most of the weight. **Measure first (E0a).**

## 1. Measurement gates (cheap, run before any lever)

**E0a — memtile→core link rate (new probe, sim-exact first, one ≤ 90 s window).** `bw_probe.rs` measures shim↔memtile only (`bw_probe.rs:17-24`); nothing measures memtile→core. Design: a **finite** memtile source (chain of BDs totalling `N`×4 KiB, the pattern of `bw_probe.rs:32-38`, so no residual stream words survive a context reuse) replayed by one MM2S through the existing A route into a core S2MM sink; the sink BDs **release** `A_FULL +1` per 4 KiB but never acquire (no producer gating), and a LockOnly-style core counts `N` acquires then releases `C_FULL` so the existing C path yields the shim token (`gemm_core.rs:205-206`, `gemm_array.rs:80-83`). Slope over `N` = cycles per 4 KiB at the sink: (i) release-only sink, (ii) the V8 2-slot acquire/release ring, (iii) 8 KiB BDs. Reading: (i) ≈ 512 → the link delivers ~8 B/AIE-cycle and overhead dominates (L2, L6 pay); (i) ≈ 1024 → 4 B/cycle, byte-bound (L4 carries). Kill for L2/L6: (ii) ≈ (i) within 5 %. The core-count/token completion proof must be simulator-exact before the window.

**E0b — per-wave vs per-chunk split, zero code, one window.** V9 `--ctl-probe nocompute`, fixed M=4096 N=2560 (40 waves), K = 64/128/320/640 (kc 1/2/5/10): `T(kc) = 40·F + 40·kc·c`. Intercept gives F on one variant (the report's 5800 came from two different designs, `report.md:457-460`; Plan A §3 makes the same objection). Kill for the "F" levers: F < 1500 cycles → per-wave overhead is not a lever for gate_up (16–24 waves) and worth ≤ 10 % for down.

**E0c — on-silicon stall attribution [INFERENCE, firmware-dependent, hazardous].** The TXN format defines `READ_REGS` (0x82) and `RECORD_TIMER` (0x83) custom ops (`ref/aie-rt/driver/src/common/xaie_txn.h:49-55`, `ref/mlir-aie/include/aie/Runtime/TxnEncoding.h:63-66`); `txn.rs:34-70` implements only write/mask/poll/sync/patch. If the NPU5 firmware honours READ_REGS, the core performance counters (events for memory conflict / lock stall / stream stall, `xaie_events_aie2p.h:236-244` cited in `gemm_core.rs:49`) would split the 290 stall cycles per chunk directly. Payload format and firmware support are not in the checked refs; an unsupported op may hang the context or the firmware, so this falls under the declared-hazardous regime (L7 policy: declare first, own window, last, opt-in flag). Not on the critical path; only worth a window if L1 fails to move the slope.

## 2. Levers, ranked

Format: mechanism · honest ceiling · kill experiment · touches · prior attempt · dependency on the backing-path track.

### L1 — De-collide the pair's A reads by swapping the Upper core's half order (compute term)
- **Mechanism.** Both pair cores run the same wavefront in lockstep (re-synchronised every chunk by `PEER_FULL`/`PEER_EMPTY`, `gemm_core.rs:719-731,753-771`), and both read `p0 = E half` at row-0 load times and `p1 = O half` at row-1 times (`gemm_core.rs:706-714,392-396,422-426`). The E half lives in the lower core, the O half in the upper core, so at every A-load cycle both cores hit the *same* physical bank of the *same* tile. The bank model counts 1024 peer-A collisions per chunk and says base relocation cannot remove them (`gemm_core.rs:58-63,1124`). Swap, for `PairRole::Upper` only, `p0 ← own O`, `p1 ← South E`, and swap the C row pointers `p4/p5` (and `p6/p7`) so the C layout is unchanged (`gemm_core.rs:487-489`): at any cycle each core then reads its *own* tile for A while the peer reads the other tile. No DMA, lock, route or host change.
- **Ceiling.** Attacks the 290-cycle stall term only (`report.md:420`). If peer-A collisions are half of it: 1357 → ~1210 cycles (est.), compute-only 37.1 → 41.6 gate_up / 44.5 → 49.9 down. Cannot exceed the 1070 schedule. Does nothing for DMA or DDR.
- **Kill.** Simulator: `gemm_core_pair_bank_access_model` (`gemm_core.rs:1131-1222`) must show peer-A collisions 1024 → 0 and the pair sim (`peacemaker-npu-sim --test gemm_core_pair`) exact. Silicon: one window, V9 layout 0, `--ctl-probe repeat=2/3` slope (`report.md:336-338`). Dead if the slope stays ≥ 1330.
- **Prior attempt.** Four base layouts were swept (`report.md:413-418`); the order swap was not tried — the module doc explicitly says relocation cannot fix it. Plan A's lever 3 ("balanced peer phase/order") is the same target; this is the concrete 4-line form.
- **Backing-path track.** Independent.

### L2 — Deep memtile A ring via one iteration-stepped BD (array delivery term)
- **Mechanism.** V9's A path is three 2-deep stages: shim BD → memtile A ping/pong (4 KiB each, `gemm_array.rs:99`) → core ping/pong. Every 4 KiB the shim stream is back-pressured on `A_EMPTY` and resumes, re-exposing DDR latency (~0.5 µs ≈ 900 cycles) per chunk; with 2 slots that is not hidden. 1470 vs 1024 cycles per chunk in the DMA-only probe is consistent with this (est.). A memtile ring of 8–16 slots needs **one** S2MM BD and **one** MM2S BD using `iteration` (word 6) with `step = 1024 words, wrap = D, next = self` and a counting lock pair (acq −1 / rel +1) — the pattern V9 already uses for B replay (`gemm_array.rs:103-109`, `dma.rs:160-170`). Capacity: V9 at kc=40 ends at `0x64000`, 112 KiB free (Plan A §4.2); down (kc=10) has far more.
- **Ceiling.** Array delivery only: 1470 → ~1100 cycles/chunk (est., bounded by the core 2-slot ring). DMA-only gate_up 0.86 → ~0.66 ms; real kernel then compute-bound (1357) → ≤ 33.5 gate_up if overlap were perfect (today 25.4 with imperfect overlap). For down: 400·1100 + 40·F.
- **Kill.** E0a(ii) vs (i): if the lock ring already runs at link rate, latency is not the loss and L2 is dead. Then simulator (odd/even `kc·waves` restart, `crates/peacemaker-npu/tests/array.rs` V9 cases) and one window: V9 nocompute with ring depth 2 / 8 / 16; dead if < 10 % on the nocompute time.
- **Touches.** `gemm_array.rs:953-1207` (V9 descriptors/locks/ring tasks), `dma.rs:151-170`. The report's "worker branch `npu/aring` unfinished" (`report.md:487`) **does not exist as code**: `git log main..npu/aring` is empty; the branch points at `0015e45`, an ancestor of main. Start from scratch.
- **Prior attempt.** None on silicon.
- **Backing-path track.** If a faster backing path shows lower latency as well as higher bandwidth, L2's gain shrinks; if the port is the limit, L2 is the only way to use it fully.

### L3 — Lock-protocol diet — withdrawn to ≈ 1 %, dropped from the 48 h
- **Mechanism (as first proposed).** The pair protocol emits 8 lock ops per chunk: acq A_FULL, rel PEER_FULL, acq peer PEER_FULL, acq B_FULL; rel B_EMPTY, rel peer PEER_EMPTY, acq PEER_EMPTY, rel A_EMPTY (`gemm_core.rs:719-731,753-771`), each `LCKREQ` 4 issue cycles plus grant latency (`gemm_core.rs:299-308`). BD lock values are signed 7-bit (`dma.rs:100-110`; rings use ±1, `gemm_core.rs:906-907`), so the owner's DMA could release `A_FULL +2` for two readers and acquire `A_EMPTY −2`.
- **Why the FULL side is unsafe (Plan A).** A shared FULL credit is fungible: if the peer is a chunk behind, the owner laps to the same slot, consumes the peer's unconsumed credit and reads stale data — the refill cannot have happened (it needs both EMPTY releases). Correctness must not depend on timing; a per-reader credit needs a second lock the BD cannot release. **Withdrawn.**
- **What survives.** The EMPTY side only: DMA acquires `A_EMPTY −2`, each core releases `+1` (the owner's own, the peer's through the neighbour lock view, `gemm_core.rs:111-120,715-718`); a reader cannot release twice without an intervening FULL, which needs the refill, which needs both releases. Saves one op (`acq PEER_EMPTY`): 8 → 7, ≈ 15 cycles ≈ 1 % (est.). Not worth a window on its own; fold into L1's program if convenient.

### L4 — Geometry for gate_up: 256×1280 wave, TN = 80, A×1 B×1, no padding (conditional feasibility, not a forecast)
- **Mechanism.** Core tile 128×80 (10 N-blocks of 8): C = 40 KiB i32, A halves 2×4 KiB, B 2×5 KiB = 58 KiB, Cout **in place over the C tail** (reverse-order SRS: block `j` writes `30 KiB + 64 j` while unread blocks occupy `[0, 256 j)`; `30720 + 64 j ≥ 256 j` for all `j ≤ 160`, and each write lands in a block of index ≥ `j`, already read). Array: core `(c, r)` owns M-block `r/2` (vertical pairs share A exactly as V8, `gemm_array.rs:43-49`) and N-tile `2c + r%2`, so the wave is 256 (M) × 1280 (N). gate_up: NW = 1 → A read **once** (10 MiB), B resident in full (400 KiB/column: column `c` holds only its two N-tiles × 2560 K), C 5 MiB → **18.1 MiB** vs 39.75 today. Each memtile replays **two** 5 KiB B streams per chunk on **two** MM2S channels (rows `h` / `h+2`; a single lane would take 2560 cycles and cap at 29.5 — Plan A); channel budget 6 MM2S: C drain 2, B 2, A injection 1 in the four injecting columns. Memtile per injecting column: B 400 + A ring 16–32 + C slots 2×4×10 = 80 → 496–512 KiB, zero slack; non-injecting columns have 32 KiB spare (not 112 — corrected per Plan A).
- **Startup.** A whole-B barrier would cost 3.125 MiB / 55.4 GB/s = 59 µs = 11 % of the 537 µs budget per submit. Required: **prefix-ready B** — per B tile and per column, the fill is a per-chunk BD (iteration over chunks) releasing its own `TILE_FULL +1` per chunk (the current single finite BD cannot publish per-chunk readiness); task 1 = pass-0 replay BD iterating over chunks (`step` one chunk, `wrap = kc`, acquire `TILE_FULL −1` per load) queued with `repeat = kc`; task 2 = whole-tile replay BD, no lock, `repeat = MW−1` (task repeat ≤ 256, `bw_probe.rs:67`; queue mechanics `gemm_array.rs:187-190`). Completion of pass 0 is what proves the tile resident before the unguarded passes. Two B tiles per column → two independent credit locks and two replay channels; **no shared credits** (see L3). Same scheme for V10 (L2b).
- **Ceiling.** MAC floor 59.0; DDR floor 108 (read) / 95 (mixed 67.2 GB/s). Budget at 50: 1510 cycles per 1280-VMAC chunk all-in (1.18× the schedule, vs 1.27× measured today) — **L4 does not reach 50 by itself; it makes 50 arithmetically possible for gate_up**. Per-core input 9 KiB per chunk = 7.2 B/cycle at issue rate, 6.1 at the 50 budget, vs 5.57 delivered today → needs L2/E0a. In-place Cout requires chunk 0 to acquire `C_EMPTY` before its first store (as the I32 path does, `gemm_core.rs:869`), i.e. the full 10 KiB tail drain is exposed once per wave: 16 waves × 2560 cycles (at 4 B/cycle) ≈ 5 % (est.). The new 64 KiB map cannot keep C alone in double banks 2–3 as layout 0 does (`gemm_core.rs:129-134`): A or B must share a double bank with part of C, so the bank model must be re-run before any number is attached. Plan B's own unmeasured estimate with L1+L2+L4 landing: gate_up 40–45; **not** a consensus forecast (Plan A: conditional feasibility only).
- **Not for down.** In-place Cout would expose the drain once per 10-chunk wave (≈ 20 % est.), and V10 already gives A×1/B×1 at TN = 64 for K = 640 (`kc·(2+NW) = 70 ≤ 112`, `gemm_array.rs:140-147`). down = V10 + L1 + L2 + L2b.
- **Kill.** Sim-only first: wavefront generator for 10 N-blocks (`gemm_core.rs:413-471`: 40 groups, new `MODIFIERS`, `pair` E/O step logic; the Ldb slot stays at one VLDB per VMAC as today), bank model on the new map, 64 KiB map (`gemm_core.rs:1102-1115` asserts ≤ 0x10000), memtile BD/lock budget (48 BDs, 64 locks, `gemm_array.rs:103-115`), prefix-ready B fill/replay ordering proof, in-place Cout retirement proof (C_EMPTY/C_FULL ownership across waves). Dead on paper if the memtile map does not close at kc=40 or the bank model shows more compute collisions than layout 0. Silicon: one window, 256×1280×640 small checks + gate_up exact + nocompute.
- **Touches.** `gemm_core.rs` (wavefront, epilogue, layout), `gemm_array.rs` (new variant: routes, descriptors, pack/unpack), `npu-gemm` CLI. One owner; largest slice.
- **Prior attempt.** Narrow waves were rejected for *more* DDR bytes (`report.md:340-346`) — that analysis kept A streamed per N-wave; with NW = 1 the objection inverts. Plan A's "two full waves + 1024×256 tail" keeps A×3 (read roof 42.8, Plan A §4.4) and cannot reach 50; Plan A's two-N-wave grouping (A×2, 23.75 MiB) is dominated. 128-wide quad A sharing is dead: cores reach only South/West/North memories (`gemm_core.rs:111-116`), not two hops.
- **Backing-path track.** If the port stays ~55 GB/s, L4 is mandatory for gate_up; if a faster path exists, L4 still removes the padding (precondition 1).

### L2b — Prefix-ready B fill for V10 (down)
- **Mechanism.** V10 fills the whole B segment with one finite BD that releases `B_FULL +MW` at the end; the first wave waits for all of it (`gemm_array.rs:148-151,166-169`; modelled startup `NW·kc·1024` cycles, `gemm_array.rs:1525-1527`). 1.5625 MiB / 55.4 GB/s = 30 µs per submit = 5 % of V10's 584 µs today, 11 % of the 268 µs budget at 50. Replace with L4's two-task scheme: per-chunk fill credits; pass 0 = replay BD iterating over the **whole segment's `NW·kc` chunks** (50 for down) acquiring −1 per load, `repeat = NW·kc`; passes 1..MW−1 = the existing lock-free whole-segment BD, `repeat = MW−1`; the TXN reset path must restore both tasks' phase (`gemm_array.rs:170-174`).
- **Ceiling.** ≤ 5 % today, ≤ 11 % at target (est.). **Kill.** Sim (odd/even restart cases of `crates/peacemaker-npu/tests/array.rs` V10); one window V10 down exact + nocompute; dead if < 3 %.

### L5 — int4 B (weights) consumed natively via `bmode = 8x4` — contract change, unsized
- **Mechanism.** AIE2P's vector config has `BMODE_8x4 = 0` alongside `BMODE_8x8 = 1` (`ref/llvm-aie/llvm/lib/Target/AIE/aie2p/AIE2PInstrPatterns.td:35-38`); the kernel sets `r2 = 0x308` = amode 0 / bmode 1 (`gemm_i8.rs:22-25`). int4 B halves B DDR bytes, memtile footprint (gate_up B 200 KiB/col → L4's map gets slack, or V10-style all-B residency at kc=40 fits: `40·(2+NW)` → effectively 40·(2+1.5) = 140 > 112, so still only with L4), per-core B stream (6.5 KiB/chunk → 4.4 B/cycle at the 50 budget, under today's 5.57 delivery — the only lever that puts the array-delivery term *below* today's measurement), and B bank traffic. If the 8x4 mode also doubles MACs per instruction (unknown; the output shape of the 8x4 VMUL is not in the inspected sources) the MAC floor halves.
- **Ceiling.** Unsized: depends on (a) whether the Flash-Next experts are int4 at rest (the model is `qwen3.8-flash-next.mq4`, `report.md:258` — suffix suggests 4-bit; not verified) so that "exact vs CPU reference" is redefined as int8×int4→i32, which is a project decision, not an engineering one; (b) 8x4 throughput. Without (a) this lever is forbidden by the exactness constraint.
- **Kill.** Ask the maintainers whether the int4-weight reference is acceptable. If yes: simulator (`peacemaker-npu-sim`) must model bmode 0 — if it does not, the first cost is a simulator extension; single-core `gemm_i8` 64³ in bmode 0 vs an int8×int4 CPU reference; one window.
- **Touches.** `gemm_i8.rs:22-25`, `gemm_core.rs:353-358` (VMUL/VMAC operands), pack/unpack, reference.
- **Backing-path track.** Independent; strongest when the port is the limit. **Scope:** outside the joint plan (Plan A rejects any reference change; agreed that it is not sought by this plan). Kept here as the one lever that changes the bytes/MAC equation if the contract is ever opened.

### L6 — K128 chunks (halve per-chunk handshakes) — conflicts with L4
- **Mechanism.** Chunk = 128 K: A half 8 KiB, B 8 KiB per slot; all per-chunk fixed costs (9 locks, BD loads, two ring handoffs, DDR resume) amortise over 2048 VMACs. Map: A 2×8 at 0x0000/0x2000 (fills the free holes at 0x1000/0x3000, `report.md:486`), B 2×8 at 0x4000, C 32 KiB at 0x8000, Cout in place → 64 KiB exactly.
- **Ceiling.** Per-chunk overhead ≈ 1470 − 1024 = 446 (DMA) and ~60 control + part of 290 stalls (compute): halving gives ~−200 cycles per 1024 VMACs ≈ 10–15 % (est.) on the array term. Mutually exclusive with L4 (TN = 80 needs 58 KiB at K64; K128 would need 86 KiB). Choose L4 for gate_up; L6 is the down-only alternative if L4's wavefront proves too costly.
- **Kill.** E0a(iii) 8 KiB vs 4 KiB BDs; dead if per-byte cost is unchanged.
- **Touches.** `gemm_core.rs:74-110` constants, wavefront chunk loop, `gemm_array.rs` BD lengths.

### L7 — Shim BD AXI attributes: AxQOS / AxCACHE — hazardous; `AxQOS = 15` wedged the device; opt-in only
- **Mechanism.** Every shim BD hard-codes burst 3 (max, aie-rt's 32-beat code, `ref/aie-rt/driver/src/dma/xaie_dma.c:765-779`), `AxCACHE = 0b0010`, `AxQOS = 0`, `SMID = 0` (`dma.rs:182-183`; fields `ref/aie-rt/driver/src/global/xaie2pgbl_params.h:16363-16390`); `bw_probe.rs:50-52` states no option exists. The NPU is non-coherent (`ref/amdxdna/…/amdxdna_gem.c:977-983`), so AxCACHE is unlikely to change DRAM behaviour; AxQOS may change fabric arbitration **against the GPU** (§4).
- **Ceiling.** Standalone: ≤ the gap between 55.4 GB/s and whatever the port can do (unknown, est. 0–10 %). Concurrent: up to the 13 % the NPU loses to the GPU (`report.md:475`).
- **Outcome (project report, 2026-10-02).** The backing-path track's `--sweep-axi` with shim `AxQOS = 15` **hung the SoC fabric on the test machine**; the NPU wedged and SMU resume failed with −22. the test machine was force-rebooted (back 22:54:48 UTC, amdxdna initialised cleanly); health window: V8 FastSlowCtl int8 512² exact, gate_up 2 s loop exact at 19.88 busy / 16.17 wall, matching pre-incident V8 numbers (`report.md:318`).
- **Policy (project policy after the incident).** A wedged NPU is a ~30 s recovery (SysRq on the test machine), so informative hazardous probes are allowed under three conditions: (1) declare the exact config and the wedge risk first; run it alone in its own window and last in that window; (2) the emitter rejects risky attributes (nonzero AxQOS, non-vendor BD word-5) by default — an explicit opt-in flag for that probe only; (3) on wedge (timeouts, SMU −22, missing `/dev/accel/accel0`) stop and report; the operator reboots; after recovery the first window is the standard health check.
- **Status.** `AxQOS = 15` is a known wedge, never repeat it. The field is evidently honoured by the fabric, so lower classes (e.g. 1, 4, 8) could still answer the concurrency question (§4) — but only after L4 has shown whether bytes alone fix the 13 % M4 loss, and only as a declared, opt-in, last-in-window probe. AxCACHE/SMID: no evidence they are safe; same regime. Low priority; not in the 48 h order.

### L8 — Backing memory and translation (branch on the backing-path track)
- **Mechanism.** BOs are `drm_gem_shmem` 4 KiB pages (`amdxdna_gem.c:582-584`) reached through **SVA/PASID** (`amdxdna_pci_drv.c:78-91`): the NPU walks the process page tables, so a 55 GB/s stream is 13.5 M IOTLB translations/s at 4 KiB. The GPU's "VRAM" on Halo is the same LPDDR5X; the only physical differences a backing type can make are translation (page size, ATS) and coherency attributes, not DRAM speed. `force_iova=1` (`amdxdna_iommu.c:13-15,132-161`) switches to a driver-managed IOMMU domain (`iommu_map_sgtable`, `amdxdna_iommu.c:66-67`) — a module parameter, i.e. a **host change → proposal only**. A user-space-only test of the page-size hypothesis: import a dma-buf whose VA mapping has 2 MiB PTEs (hugetlb memfd via `udmabuf`, if `/dev/udmabuf` is accessible) through `Device::import_dmabuf` (`crates/railgun/src/npu/mod.rs:347-381`); the HIP VMM host path already proven (`report.md:376-401`) likely maps 4 KiB PTEs [INFERENCE].
- **Ceiling.** Read path only. Even an unbounded port leaves gate_up at ≤ 37.1 (compute) today and down at ≤ 29.5-eq (array, V10 nocompute). Value is in removing the 13 % concurrency loss and the DDR term after L4.
- **Branches.** (a) *faster path exists*: adopt for A/B/C; re-run E0b (F may include latency); L2's value drops. (b) *needs a driver change*: write the proposal (force_iova + large-folio mapping, or P2P attach so amdgpu keeps VRAM — `amdgpu_dma_buf.c:127-157` cited in `report.md:382-383`), proceed with L1–L5 unchanged. (c) *port-limited at ~55 GB/s*: bytes/op is hard currency → L4 mandatory for gate_up, L5 escalated, L7 for concurrency.

### L9 — Fuse gate_up → down (keep the 4096×640 activation on-chip)
- **Mechanism.** Saves gate_up's C write (5 MiB) and down's A read (2.5 MiB after L4; 12.5 MiB today) by computing `silu(gate)·up` + requant on the cores.
- **Ceiling.** ≤ 7.5 of ~32 MiB combined traffic after L4 (≤ 23 %), 0 % of compute, 0 % of array delivery; and the activation is a float op whose bit-exactness against the CPU reference is a new contract (AIE2P bf16/fp32 paths exist, `AIE2PInstrPatterns.td:69-70`, but matching the host's silu/requant bit-for-bit is not established). The intermediate (2.5 MiB int8) does not fit beside L4's resident B (3.2 MiB) in 4 MiB of memtile.
- **Verdict.** Drop for the 48 h; revisit only if bytes become the sole remaining term and the activation contract is settled by the project.

## 3. Dropped levers (with the evidence)
- **Overlapping submits / persistent context.** Wall ≈ busy already (`report.md:436-437,480`). The per-submit *startup* (whole-B fill barrier: V9 one N-wave tile 1.25 MiB ≈ 24 µs, V10 whole B 1.56 MiB ≈ 30 µs, L4 3.125 MiB ≈ 59 µs at 55.4 GB/s) is not a submit-overlap lever but a fill-ordering one → L2b / L4 "prefix-ready B".
- **More shim channels / second A channel.** 8×1 = 53.7 vs 8×2 = 55.4 GB/s (`report.md:330`): aggregate, not per-channel, limit.
- **Burst length.** Already maximal (`dma.rs:182`).
- **NPU DPM / clock.** No QoS → max DPM level (`ref/amdxdna/…/aie2_solver.c:120-123`; `crates/railgun/src/npu/mod.rs:405-411` passes a zero `QosInfo`); array measured at the 1.80 GHz H-clock (`report.md:174-177`).
- **Narrower 512-column waves (TN=64, 1024×256).** More A re-reads (`report.md:340-346`, Plan A §4.4). Superseded by L4.
- **Horizontal B sharing between columns.** Needs an East memory view; cores have South/West/North only (`gemm_core.rs:111-116`).
- **C direct core→shim (skip the memtile).** Two cores per shim S2MM channel would interleave packets in arrival order; the host layout would be non-deterministic. Dead.
- **i32 epilogue variants.** int8 SRS already in place; i32 was 4× the C bytes (`report.md:316,441`).
- **C tile >128×64 to amortise F.** 128×128 i32 = 64 KiB = the whole data memory.

## 4. Running beside GPU prefill (M4: GPU −10.1 %, NPU 25.6 → 22.2, `report.md:466-475`)
- The shared resource is the fabric/DRAM port; the NPU's loss (13 %) and the GPU's (10 %) both scale with NPU bytes/s, so **L4/L5 are concurrency levers too**: gate_up 39.75 → 18.1 MiB per submit halves the NPU's demand at equal TOPS.
- **AxQOS (L7)** is the only knob that changes arbitration rather than volume; `AxQOS = 15` **hung the fabric**. Under the declared-hazardous regime (L7 policy) a lower class could be probed once, alone, last in its window, opt-in flag only — and only after L4 shows whether bytes alone recover the 13 %. Until then concurrency relief comes from bytes (L4/L5) and scheduling.
- **Phase-aware co-scheduling** (hipfire dispatch side, Rust): run NPU GEMMs during GPU phases that are not DRAM-bound (attention / small-M kernels) and hold them during GPU GEMM/pp phases. Unsized: needs the GPU's per-phase FETCH_SIZE/WRITE_SIZE profile (`report.md:259` pmc mode). Kill: if GPU prefill is DRAM-bound throughout, there is no window to exploit.
- **Partitioning columns** (num_tiles < 32, `report.md:265`) does not reduce port contention; it only matters if a second NPU client exists. Not a throughput lever.
- Zero-copy A from the GPU is proven (`report.md:388-400`) and costs nothing (22.65 vs 22.70); it removes host copies, not NPU bytes (agrees with Plan A §4.5).
